### 2.3 一岗一库（【已定】+【已实测】，本场拍板）

- **落点**：`data/chat/<岗位号>/job.db`（跟 `state.json` 同级；第一次采集时才建）
- **为什么**：数据跟岗位走 → "关闭/删除岗位"就是**挪目录**，库跟着走；总库那种"岗位早没了、库里留孤儿行"的毛病自然消失
  （现成反面证据：`data/business.db` 面板只剩 3 个岗，库里躺着 **3 个早删掉的岗、311 行**）
- **明确不做**：**不做总库、不做跨岗复用/人才库/索引库**（老板原话："没必要这么麻烦了，我们执行做到这个岗位的候选人不重复就可以了"）
- **"本岗内不重复"= 三道锁**（【已实测】单测覆盖）：

| 锁 | 机制 | 行为 |
|---|---|---|
| 主锚点 | `UNIQUE(job_code, source_id)`（猎聘 `res_id_encode`） | 同一个人第二次采到 → **updated，不新增** |
| 兜底 | `UNIQUE(job_code, content_hash)`（sha1(岗位号+简历原文)） | 换了 id、原文一样 → `duplicate`，不新增。**raw 为空时存 NULL**（SQLite 允许多个 NULL，多条"还没抓详情"不互相误撞） |
| 匹配层 | `UNIQUE(job_code, candidate_id)` + `raw_hash` 输入指纹 | 同输入 → 命中缓存，**不重复付费** |

- 五张表：`candidates` / `match_results` / `candidate_events` / `pool_samples` / `job_meta`
  （前三张正是老板要的"采集的候选人 / 匹配结果 / 沟通记录"；`pool_samples` = 列表页原文临时池 = 本地粗筛的原料）
- **单测当场抓到 2 个真 bug（都在库代码里，已修）**：
  1. **插入路径漏带 `content_hash`** → 兜底锁形同虚设（换 id 同原文会被当新人重复入库）；
  2. `save_match` **会把没传的字段洗成空** → "只更新分数"的调用会把 `match_points`（**话术原料**）清空。
- 验证过的行为：一岗一库隔离 / 级联删不留孤儿行 / 重复开库幂等 / WAL 已开 / **整棵目录拷走即可用**

### 2.4 参考代码深读：一个颠覆性结论（【已实测】，关键几条我自己 grep 复核）

**（a）`recruitment-wails`（Go+Wails，新版）——采集是全人工的！**

- **没有 `chrome.tabs.create`、没有翻页点按**（全库 grep：只有 `chrome.tabs.query`）→ 流程是：
  **人工设条件 → 人工翻页 → 点「采集本页」抓列表 → 人工逐个点开详情标签 → 点「批量采集」把已打开的详情页一次性收割**
- **没有配额/限速**（无 delay、无每日上限、无并发控制）——反检测靠"复用用户真实浏览器 + 人工手势"
- **没有配方表**：搜索条件不做结构化配置，唯一"条件产物"是 LLM 生成的 4 组关键词，**给个"复制"按钮让人工粘到搜索框**
- 匹配：**纯 LLM 打分**（无 embedding/向量，全仓 grep 0 命中）；`0-100` + 四档锚点（90/70/50）
  + `confidence` + `match_points ≤3` + `concerns ≤2`；
  **「猎头特别提醒」由 LLM 自行分成【硬性要求】（不满足即一票否决）/【优先规则】/【特别提醒】**；
  **合规护栏**：歧视性要求一律忽略并在 concerns 写"该要求涉嫌违法/歧视，已忽略"
- **池评与单人评分彻底拆开**：池评只喂**去重后前 50 条样本**一次调用（输出池质量+缺口+建议+**`data_valid` 采集错页自检**）；
  逐人评分**一人一次调用**；**报告端用纯 SQL/前端聚合算分数分布**，LLM 只写结论句
- **输入指纹缓存**：`sha256(岗位文本 + 候选人原文 + 特别提醒)` → 命中即跳过并提示"未重复付费"
- 每次调用 `truncate(3000)` + `MaxTokens 2048` + `temperature 0.3` + **关思维链**
- 它的毛病（正好是我们的教训）：**四维分数字段从未写入**（死字段）；"一票否决"**只在 prompt 里靠模型自觉**；
  **报告分档(70/50)与 prompt 分档(90/70/50)不一致**；**不要求引原文/给证据**；无人改分回写

**（b）老板自己的 `lietouserver/gui/自动采集候选人资料猎聘deep.py`（老版，03-21）——全自动**

- Playwright 经 CDP 直连他自己的 Chrome（`connect_over_cdp(127.0.0.1:9222)`）
- **全量翻页**（`li.ant-pagination-next` + `is_last_page`）→ 逐行 `tr:has(img.new-resume-logo)` → **逐人开详情（新标签）**
- **中英简历自动切换**（点「中文简历」，比切换前后文本长度）
- **全文**：`page.evaluate("() => document.body.innerText")`（**无 3000 字上限**）
  + `wait_for_content_stable(15 次重试 / ≥1000 字 / 连续 3 次长度不变才认为加载完)`
- 清洗 → **PostgreSQL** `candidate_pool`（`platform + platform_candidate_id` 幂等去重，命中只更新 `batch_id`）
- **真人节奏**：`between_actions()` 随机 3~8 秒、点击前后停顿、阅读停顿、滚动懒加载
- **结论：同一个问题上，老板从"全自动"退到了"全人工"**（推测原因 = "查看简历"这个风控点）

**（c）对比下来我们现在缺三块（全是老板老代码里有的）**：

| 缺什么 | 老代码怎么做 | 我们现在 |
|---|---|---|
| **翻页** | `ant-pagination-next` | ⚠️ **0 处翻页**（每关键字只抓首页 30 人） |
| **详情全文** | `document.body.innerText`（无上限） | ⚠️ **桥只有前 3000 字**（`background.js:185` 硬编码 `slice(0,3000)`） |
| **跳过已采** | 幂等去重、命中只更新批次 | 只有"合并去重"（重跑会重复抓、浪费额度） |

### 2.5 采集与匹配的形态（【讨论中】→ 已收敛到"该定参数了"）

**老板的关键判断（我同意）**：**如果每个候选人都要过 LLM，那么"先采集后匹配"与"采集匹配合并"token 几乎一样**
→ 所以**不该合并**，而应该在 LLM 之前加一道**本地召回层**。这一下同时解决三件事：省 token / 知道何时停 / 不用翻到最后一页。

**收敛出的形态**：

```
② 正式采集（本地，0 token）
   翻页 → 逐行读卡片 → 本地粗筛(A 硬条件 + B 关键词命中) → 过线者 upsert 进本岗库(新人)
   每页算通过率 → 连续掉线 → 停 + 提示"换词 / 加今日活跃" → 下一轮
③ 匹配（LLM，只对台账里"过线且没评过"的人）
   分 / 匹配点 / 疑虑（= 话术原料）+ raw_hash 缓存（评过不再花钱）
④ 详情（只对③的高分者：人工开页一键收割，或自动开前 N 个）→ 补全文
⑤ 打招呼（入围名单定了再生成话术）
⑥ 持续跟踪：每天/每轮重跑②，本地按 source_id 跳过已见 → 只报"今天新增 N 人"
```

**已拍**：
- **不合并**；加本地召回层
- 粗筛**先用 A+B（规则+关键词表，0 新依赖）**，**向量以后再说**（参考项目也没有向量；且有"项目最终要能编译/打包"的长期约束）
- 质量停止判定 = **LLM 出分、代码判线**（不用 LLM 判"掉线"；语义漂移用每 2~3 页抽样问一次）
- **落盘形态**：**边采边落盘**（不用"全内存、最后统一出报告"）——理由是老板老代码就是逐条入库的、崩了能续；我们自己的纪律也是"**恢复能力 = 落盘粒度**"
- 话术**只对过线者生成**（参考项目也是 ≥70 才生成）

**待拍**：
- 话术**时机**：匹配时"顺手生成" vs **入围名单定了再生成**（我倾向后者：打招呼是人工最后一步，口径变了一批话术就作废）
- **逐人匹配由谁执行**：**小猎**（贵/飘/但一致）vs **直连 LLM 调用**（便宜/可缓存/可断点，但要**新开一条"非小猎"的通道**，
  与"判断都走小猎"的纪律冲突）← **这是新对话要拍的第一件事**

### 2.6 "本地代码能读列表页总览吗"（【已实测】能）

`extract` 每行的 `row["text"]` 就是那张卡片的全部文本，已含：
**姓名(掩码)、年龄、工作年限、学历、城市、求职期望、当前公司+职位+在职时长、学校+专业+是否统招**，外加 `fields.res_id_encode`。
→ **粗筛完全能在列表层做完，一张详情页都不用开。** 我们唯一缺的是**翻页**。

### A.3 其它新增/删除【已查证】

### A.6 路线取舍（结论，供将来参考）

- `browser-use` 的 `attach` **技术上能替掉我们的「扩展 + 桥」**，还可能顺手解决"只能读 3000 字"；**但代价是把"确定性 + 省 token"换成"LLM 现场操作"**（点哪个元素由模型当场决定）——跟我们刚花两场治的病是反方向。**要不要换是路线问题，不是技术问题。**
- `computer-use` 建议当**后备手段**（猎聘开 F12 白屏这类反调试场景），不作主路径。
- 建议：**先学、先不升**（等②③④跑通），与"跑通再改"的一贯节奏一致。

### A.7 顺带查清的一件事：桥的 3000 字是我们自己写的【已查证】

- `bridge-agent/extension/background.js:185`：`result.body_preview = bodyText.slice(0, 3000);`（**硬编码，没做成参数**）。同函数里还有一批同类上限：元素名 80 字（6 处）、value 60 字、href 120 字、输入回显 50 字、元素总数 `MAX = 400`。
- 设计意图（**推断**：`bridge-agent` 不是 git 仓库，查不到提交历史）：整个 `zSnapshot` 是"**给模型看的一份紧凑页面摘要**"，消费它的是模型（`core.py:316 snapshot_to_text()` → `:349`）。
- **它只咬详情页**：`extract` 读列表卡片**不截断**（`background.js:518` `text: (row.innerText||'').trim()`）→ 列表信息我们拿得全。
- 改法（推荐 b）：**新增动作 `page_text`**（返回整页文本，可带上限）＝ 1 个函数 + 动作注册表 1 行 + **老板在 Chrome 重新加载一次扩展**。
- **口径**：**落盘存全文，喂模型再按预算截**（参考项目正是这么干的：存 `document.body.innerText` 全文，喂 LLM 时 `truncate(3000)`）。**3000 作为"喂模型的预算"合理，作为"存储上限"是错的**——我们现在把两件事混在一起了。
