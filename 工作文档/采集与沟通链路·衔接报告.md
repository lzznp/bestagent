### 2.3 打招呼的两条路（**实测**，这是决策 18 的平台机制证据）

**点击路径**：候选人详情页 `[立即沟通]` → **只弹对话框，不发送** → 对话框里选：

```
请选择职位开聊
├─ 开聊职位：默认已选中你的岗位（值来自 URL 的 selectedJobId=79866575）
├─ 打招呼语：猎聘自带模板库 + 老板自存话术（一长串）
├─ [立即开聊]              → 带岗位卡片
├─ [不选择职位开聊]        → 不带岗位
└─ [修改打招呼语] → /im/mycommonlanguage?sayhi=true
```

- **老板实测**：选「**不选择职位开聊**」→ **一步就用第 1 条预设语发出去了**（无需打字、无需再确认）。
- 第 1 条预设语原文：`你好~我这里有个职位很适合你，待遇优厚，了解一下吗？期待回复！`
- → **结论（重要）**：
  - **"携带岗位信息"联系** = `立即开聊`（**需要 `hjobId`**）
  - **"没发岗位、直接联系"** = `不选择职位开聊`（**不需要 `hjobId`**）
  - **平台自带这两条路，我们不需要另造机制。**

## 3. 采集链现状诊断（代码证据）

### 3.1 "混到一起"的准确含义（老板澄清）

> **原设计**：① 分析性价比 → ② **在搜索结果里瞄一眼总人数/质量**（决策点）→ 再决定要不要正式采
> **实际实现**：① 分析性价比 → ② 出搜索计划 → 认可 → **直接搜** → 直接出（③池评）→ 打招呼报告
> **→ 中间那个"瞄一眼"的决策点被吞掉了，一口气干到底。**

### 3.2 病根：一条 prompt 干两件目的相反的事

`data\prompts\analyze_job.txt` **一次调用**同时产出：

| 输出 | 面向谁 | 性质 |
|---|---|---|
| `jd_extracted` / `progress` / `score`(0-25) / `recommendation`(接单/沟通/放弃) | **老板**（接不接这单） | **人看的判断** |
| **`search_keywords`**（精确/职能/竞品/技能） | **机器**（猎聘搜索词） | **要执行的参数** |

接单分析要"全、带解释、带判断"；采集词要"短、可执行、必须能命中"——**标准相反，塞一个 JSON 必然互相污染。**

### 3.3 证据一：真实产出已经不像机器能用的东西

本单 `reports\analyze_20260909-094930.json` 实际值：

```
精确匹配: 机械工程师 非标 传动 南京 | 机械工程师 非标 传动 苏州
职能相近: 机械设计工程师 自动化设备 结构设计 | 非标自动化 机械工程师 | 物流自动化设备 机械设计
竞品对标: AGV 机械工程师 苏州 | 智能仓储 穿梭车 机械设计 |
          叉车 AGV 机械工程师 南京（对标方向：杭叉/合力/诺力/中力/极智嘉/快仓/新松/昆船/国自等AGV与智能物流厂商）
技能导向: SolidWorks 传动 电机选型 受力分析 | 非标设计 齿轮 丝杆 减速器 | 叉车AGV 机械结构设计
```

三处毛病：
1. **词串内空格 = AND** → `SolidWorks 传动 电机选型 受力分析`（4 词全要命中）、`机械工程师 非标 传动 南京`（4 词全要命中）→ **几乎必然 0 命中**；
2. **`|` 分隔多串 + 尾部夹人话注释**（"（对标方向：杭叉/合力/…）"）→ **不是纯机器可读数据**；
3. **两地写在同一串里**（南京｜苏州），而 12HC 是**南京 6 + 苏州 6** → 本该分开跑。

### 3.4 证据二：两个文件在互相打架

- `analyze_job.txt:61` 教 LLM 生成：`"精确匹配：岗位名称 + 核心技能 + 城市（如：CQE 客户质量工程师 英语 常州）"` ← **4 个词一串**
- `m3_chat.py:746` 又警告：`"⚠️ 猎聘搜索框是'包含全部关键词'——空格分隔的词全部要命中，关键字词内别叠同义词/多词，否则极易 0 命中"` ← **别叠多词**

### 3.5 证据三：采集计划那步在"修复上游脏数据"

`m3_chat.py:736-737`（`auto_job.py` 有同款）：*"从报告的 `search_keywords` 里挑 2~4 个最可能命中目标候选人的关键字"* → **计划步骤的真正职责是"把脏数据改造成合格关键字"，靠 LLM 现场判断**，**每次结果不一样、不可复现、失败时不报错只出 0 命中**。

### 3.6 采集执行链（实测代码，未改）

`collect_liepin.py`：自动发现猎聘 tab → 每关键字：`navigate` 条件页 → `click_by_text 清空筛选条件` → `execute_spec`（**配方表确定性设置**）→ `extract anchor=立即沟通` → 按 `res_id_encode` 去重 → 合并落盘。

### 4.2 流程定稿（老板选 **A**：发岗在前）

```
① 岗位分析（性价比；不看候选人池）
      ↓ 你拍板"做"
② 记录【是否发岗】  ← 你在猎聘手动做，小猎只记录（不阻塞）

      ↓ 你认可
④ 采集执行（顺便记录池子质量：总人数 + 质量初判）
      ↓
   〔分岔出口〕┬─ 继续 → ⑤ 匹配（池评+逐人评分）→ ⑥ 打招呼 → ⑦ 总沟通
              ├─ 放弃      → state: abandoned + 原因
              └─ 长期挂着  → state: watching + 复查计划
```

## 8. 关键教训（本场新增）

1. **一个 prompt 别干两件目的相反的事**（接单决策 vs 机器参数）→ 数据必然互相污染（本场采集词就是这么脏的）。
2. **平台自带的机制，先看清楚再设计**：老板描述的两条打招呼链路，其实是猎聘对话框里的**两个按钮**，不需要我们另造。
3. **"看不见的编号"要优先怀疑链接地址**（猎聘编号不在正文、只在 `href`）。
4. **同一个字段在平台侧可能是"粘的"**（`沟通职位` 留旧值）→ **不能当归属依据**；归属要靠自己的账本 + 唯一键（`res_id_encode`）。
5. **工具不应答要查机制，别猜"睡一会就好"**（这次实测 5 分半 + alarms 周期，直接推出"扩展没在跑"）。
6. **渠道归属别含糊**：参谋长的眼睛 = 侦察；小猎跑腿 = 业务链路。**本次读页面用的是眼睛**，这一点要写清楚，免得以后以为是桥读的。
