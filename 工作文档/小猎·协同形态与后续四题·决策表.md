### 决策 41【待议·本场新增】防"被封装配送"—— 威胁模型与许可证

**老板 2026-09-20 澄清真实担忧**："我不担心授权被绕过，也不担心丢失高价值的东西，我就是担心给弄到源码级别的那种——我用着不错，但是别人自己封装、自己授权给其他的人了，别人拿去开源了。"

→ **威胁模型 = 防"自成一家"**（不是防破解）：①拿到**源码级**的东西 ②换成自己的名字**封装** ③自己**授权给别人** / 自己**开源抢先**。

- ⚠️ **必须纠正（对决策 33 的补丁）**：开工书 §7.3 建议"照同业形态（MIT）开源"——**MIT 恰好允许别人闭源封装、换许可证、直接售卖**，是他最怕那件事的直通车 ⇒ **MIT 必须排除**。`recruiting-copilot` 敢用 MIT 是因为它**没有商业授权生意**（它甚至是 DSH 生态的引流件，越多人封装越有利）；我们没有这个前提。
- **三层防线（按"真能拦住什么"排序）**：
  1. **技术（唯一真正有效）**：大脑在服务端 ⇒ **源码不出门**，同事/客户手里只有壳（扩展+桥+网页）。⚠️ 附带诚实：**若给同事源码级的东西（让他们自己改），等于主动放弃这条控制权**——那是选择不是意外。
  2. **许可证（决定"别人能不能合法自成一家"）**：❌ MIT/Apache（允许闭源封装换授权售卖）｜✅ **AGPL-3.0**（衍生作品含网络服务必须开源 ⇒ "封装成闭源再授权卖"这条路死掉；且别人转发你的代码**必须保留你的版权声明**，等于替你传播署名）｜✅ 非商用许可（PolyForm NC / BUSL，N 年后转 Apache）｜✅ AGPL+商业双许可（公众免费用，商用买授权）。
  3. **归属（低成本、比加密有用）**：文件版权头 + LICENSE + **公开发布时间戳=首发证据** + **商标「小猎」**（几百块；商标能挡"别人的封装成品冒充你"，版权挡不住）。**反向提醒**：做防抄的技术保护（加密/混淆/授权体系）是浪费——wails 红队已替我们交过学费。
- **反直觉但关键**：**"别人先开源"的最好解药 = "你自己先发布"**。越晚公开，被独立实现者抢先的概率越高；署名在先则"别人再开源"失去意义。**要分开的两件事**：公开**方法/决策/数据形状**（＝这些工作文档，几乎零风险、占位收益最大）vs 公开**能跑的整链**（桥+扩展+脚本+口径，有风险、须配许可证）。
- **拦不住的**：思想与设计（写出来就拦不住）；护城河只剩"跑得快 + 口碑"（垂直小圈子，盗版封装的成品冒充不了原版）。
- **待老板拍**：更怕 (A)"别人拿你的**代码**去封装卖" 还是 (B)"别人**独立做出**并先发布"？→ 我倾向 **A+B 同解 = AGPL-3.0 + 尽早发布方法与设计**。

## 6. 【草案 · 待拍板】产品形态（同事版）——「小猎工作台」

> 老板问："假如上线了、同事们能用，交付的是什么产品？工作页面长什么样？"下面是**自主设计**（不迁就既有想法），还没拍板。
> 这是**决策 36（协同形态）的多人版展开**；建议落为**决策 40【待议】产品形态（同事版）**。

### 6.1 交付物定义

**一句话**：交付的不是软件，是**「一张今天的桌子 + 一个数字同事 + 一只长在浏览器里的眼睛」**。

| 层 | 内容 | 长在哪 |
|---|---|---|
| ① **本地轻件** | 浏览器扩展（眼睛+手，用**同事自己的登录态**）+ 桥（跑腿，**token 白名单**） | 同事的电脑 |
| ② **工作台网页** | 同事每天看的那一屏（今日/岗位/池子/沟通）；**本地模板渲染，0 token** | 内网一台机器 |
| ③ **服务端大脑** | 口径/判断/配额/prompt/数据。**同事机器上没有真相** | 内网/云一台机器 |

### 6.2 为什么是这个形状（三条硬约束推出来的，不是偏好）

1. **账号安全**：必须用同事**自己的真浏览器 + 人工节奏**（`recruiting-copilot` 无头被限 web 登录 24h 的反证）；
2. **铁律**：不可逆动作在人手上 ⇒ **产品里不许有"发送"按钮**；
3. **防泄露**：wails 红队已证"本地分发物终究可破"（试用可重置、二进制可 patch、指纹可搬家）⇒ **高价值能力只能放服务端**；同事机器上有的只是"壳"。

### 6.3 五条设计主张

1. **首页不是岗位，是"今天"** —— 顾问的痛不是"某个岗怎么跑"，是"我现在该干哪件"。现有系统全是一岗一流程（步骤制），所以第一天就会被问"我该先干哪个"。
2. **产品里没有"发送"** —— 产出物是**"可粘贴的话术 + 跳转链接"**，动作永远在人手上（铁律 + 风控一举两得）。
3. **给人看的一切都是本地渲染的静态页（0 token）**，小猎只产小 JSON（沿用"数据/展示分离"）。
4. **同事机器上没有真相** —— 口径/客户/候选人数据在服务端；顺带解决"同事离职带走资料"。
5. **一份基因，多个分身** —— 基因（口径/纪律/话术）只有一份；分身 = **账号与数据隔离**（每个顾问只见自己的岗与候选人）。这是"一个脑子 + 多个壳"在多人场景的正确读法：脑子=同一套代码与口径，分身=数据与账号。

### 6.4 主界面（今日页）

```
┌────────────────────────────────────────────────────────────┬──────────────┐
│ 小猎工作台   今天 9-21 周一   [王顾问] ●桥在线 ●额度 41/50  │  小猎（对话） │
├────────────────────────────────────────────────────────────┤              │
│ 今天：该跟 6 人 · 新回复 2 · 岗位待处理 3 · 🔴1              │ 你：这人是谁 │
├────────────┬───────────────────────────────────────────────┤ 小猎：程**， │
│ 岗位       │ 🔴 待你决定                                   │ 机械工程师， │
│ ● 机械工程 │  ┌─────────────────────────────────────────┐  │ 9/19 打过招呼│
│   停：沟通 │  │ 程** 回复："方便发一下岗位职责吗？"      │  │              │
│   待处理 2 │  │ 建议：您好，职责我发您，另外先确认…      │  │ [复制话术]   │
│ ● 后端设计 │  │ [复制话术] [打开会话] [跳过]             │  │              │
│   停：采集 │  └─────────────────────────────────────────┘  │              │
│ ○ 会计     │ 🟡 该跟进（4）／ 🟢 在跑（3）／ ⚫ 红灯（1）  │              │
│ [+新岗位]  │                                               │              │
└────────────┴───────────────────────────────────────────────┴──────────────┘
```

- **左栏**：岗位导航（状态灯＝停在哪一步 / 待处理数）——一岗一库的可视化；
- **中栏**：**今日卡片流**，四类：**🔴待你决定**（回复话术/是否止损/额度怎么分）｜**🟡该跟进**（时间驱动）｜**🟢在跑**（进度）｜**⚫红灯**（风控页/额度将尽/桥掉线）；
  **卡片排序 = 小猎的经营判断**（哪个先干）——这正是**决策 21「多岗并行·待我处理」总览**，也是 `重走复盘 §4` 说的"老板所有乱的源头"；
- **右栏**：小猎对话**常驻**，任何页面都能问"这人是谁／咋回／这岗啥情况"。

### 6.5 其余页面

| 页面 | 是什么 | 为什么不能并入今日页 |
|---|---|---|
| **岗位页** | 一岗的生命周期时间线（分析→寻源→池子→打招呼→沟通→台账）+ 每步产物链接 | 接手别人的岗、回头看、给客户汇报 |
| **池子页** | 表格/卡片式结构化审阅（报告卡片+表格） | "翻大池子"不适合对话（已有结论） |
| **沟通页** | 会话视图（谁回了/我发过什么/上下文/话术/跳转） | 主战场，需要连续上下文 |

### 6.6 角色

**顾问**（只见自己的岗与候选人）｜**主管/老板**（全岗 + 经营视图：额度分配、进度对比、谁闲着）｜**助理**（只录入整理，无判断权）。页面同构，权限不同。

### 6.7 MVP 与判据

- **MVP** = 本地网页（今日 + 沟通）+ 扩展（指认 tab / 读当前会话）+ 大脑在老板机器或内网一台；**不做多租户**。
- **判据**：**同事第一周每天都打开它**（因为"今天该跟谁"只有这里有）。做不到 ⇒ 设计失败，不是推广不力。
- **明确不做**：自动发消息 ｜ 手机 App ｜ 多租户计费 ｜ 花活（AI 打分/代写简历）。

### 6.8 技术选型判断（与现状冲突的一条，需老板知悉）

现有 **Streamlit 面板不适合当同事版工作台**（三栏交互 + 一键复制 + 与浏览器联动都别扭）→ 工作台用**本地渲染的网页**（沿用 `report_html.py` 那条"数据/展示分离"路线），**面板退为"执行台"**（跑采集/评估等重活）。

### 6.9 待老板拍的两条（其余都是我的设计决定）

1. **服务端形态**（要一台常开机器；胜在防泄露 + 免维护同事机；败在运维成本）**vs 每人本地全套**（胜在零运维；败在真相落到同事机器 + 维护地狱）；
2. **团队几个人、有没有一台可以常开的机器**。

### 6.11 【本场新增 · 待议 决策 42】自己团队 vs 外部团队：数据放谁的机器

**老板新增担忧**（原话）："我们现在这个 py 源码运行的状态其实更适合小猎，但是我担心，我弄个批处理启动了代码，同事们用着比较舒服，然后有个同事离职了，U 盘拷贝走了一切。"

- **先给结论**：这**不是产品形态问题，是"数据放在谁的机器上"问题**。而且**无技术解**——只要数据与"他能运行的程序"同在一台机器，U 盘一定能拷走（**加密也不行：要跑就得能解**；与 wails 红队"本地分发物终究可破"是同一条）。→ **只有两条路：①接受 ②数据不落他机器。**
- **我上一轮把两件事混了，纠正**：
  - **自己团队** → 数据集中到**老板的机器 / 公司内网一台机器**（这是本分，不是给外人当服务商）；
  - **外部团队** → 给一整包（程序+数据都在他们那边），**他们的离职风险是他们的事**，老板不运维、不负责。
  混着谈才会出现"要么必须架服务器、要么完全不管"的两头堵。
- **自己团队版形态：手脚在同事机器，大脑与数据在老板机器**

  | 在哪 | 是什么 | 有数据吗 |
  |---|---|---|
  | 同事机器 | 浏览器扩展（读**他们自己的**猎聘登录态）+ 桥（跑腿，token 白名单） | **零数据** ⇒ U 盘拷走＝拷走一个跑腿程序 |
  | 老板机器 | 工作台页面 + 大脑（判断/口径）+ 数据（岗库/台账/客户名单） | **全部真相** |

- **拦不住的（诚实）**：他脑子里/微信里的候选人、屏幕截图、他自己的记忆——任何形态都拦不住；**若他能登录老板的机器，一切免谈** ⇒ 只给浏览器访问，**不给机器账号**。
- **两条便宜加固**：①**审计日志**（谁在何时看了/导出了哪些候选人）——**威慑力最大**；②**制度层**：保密协议 + 客户归属条款（技术对人心无效，这才是对"人"的有效约束）。
- **反向提醒**：**别为了防离职去打包 exe**——打包只解决"装得上"，不解决"拷得走"；**py 源码运行态改得快，更适合现在的小猎**。
- **战略层（真正的解）**：离职带走客户是猎头行业常态，防不住。行业里真正有效的是"**客户关系在老板手上 + 候选人库集中 + 流程不依赖某个人的私人微信**"——**小猎本身就是在做这件事**（把候选人与岗位从个人微信/Excel 搬进公司库）。⇒ 小猎既是效率工具，也是**防资产流失的基础设施**。
- **待老板拍**：①团队几个人、是雇员还是合作顾问（决定制度层能做到什么）②能不能接受"**数据都在老板机器上、同事只开浏览器**"（代价：老板的机器要常开；收益：离职拷走＝0）。

> **【2026-09-20 补 · 老板澄清】**数据 / 简历**不是本场关切**（"那是数据归属方的事情"）；本场关切收敛为**"他自己的那套源码"**。⇒ §6.11 整节是**数据视角**，**对"源码问题"无效**，此处仅作存档。

### 6.12 【本场收敛 · 待议 决策 43】"白嫖"的真答案：资产不是源码，是决策链

**老板原话**（2026-09-20）："人家随便让 AI 一下子弄到源码级别，AI 再参考一下，做个 mac 版的呢……我们为这个小猎也捯饬了一个月了，基本上和 deepseek-harness 同步了吧，我们讨论了多少时间，花费了多少 token？我们修正了多少次，我们踩了多少坑？**我不想让别人那么容易白嫖**，所以我赌气说开源，但是啊，我水平菜，开源？有点班门弄斧啊。"

- **资产位置算错了（本节核心）**：**源码是果，决策链是根**。这一个月真正的沉淀 = **30+ 份工作文档**（开工书 / 决策表 / 衔接报告）：决策 31/32、桥的来源白名单、⑤查看回复里单测抓出的两个真 bug、发布红线与沟通口径……**源码 AI 一天能重写，决策链是三十次踩坑换来的。** ⇒ **"防白嫖"的最优解不是藏源码，而是让源码离开本环境后不值钱**（空口径、无台账、无岗型方案、无同步经验）。
- **自带护城河（此前没人意识到）**：**"和 DSH 同步了一个月"＝强耦合**。抄走快照的人，DSH 一升级就得自己重修一遍；而我们有踩坑记录。⇒ **每次升级踩的坑，都是往护城河上加土**（建议把升级踩坑记成册）。
- **白嫖经济学**：**不付钱的人本来也不会付钱** ⇒ 防他们收益≈0、成本>0。真正值得防的是"拿你的东西做成产品去卖"的人，而那要同时具备**拿到源码 + 能做产品 + 有渠道卖**，且这种人通常自己重写更快。
- **Mac 版不构成威胁**：战场是 Windows + 猎聘/禾蛙 + 桥 + DSH 同步；重做一遍是数百小时，真做出来时我们已经在跑单挣钱了。
- **"开源＝班门弄斧"是误判**：开源不是炫技评审，**是发布渠道**；而且**现在根本不必开源**。真到要发布那天，**发"工程过程"比发"代码"更合适**——过程＝决策链，AI 抄不走（这也正是决策 33"骨架 vs 口径"分层的**真正理由**）。
- **"赌气说开源"应收回**：赌气的决定两头不讨好（既不保收益，也没换声誉）。冷静版 = **不宣布、不承诺**：先私有跑单，把"发布"留成一个按钮，**选择权握在手里**（＝决策 33"先私有"维持，但**理由从"防泄露"改为"保住选择权 + 让白嫖无收益"**）。
- **建议动作（最贵的一条也就几百块）**：①**不宣布、不承诺**（0 成本）②**把过程资产系统化**（rules.md / 岗型方案 / 升级踩坑册）③**归属三件**：LICENSE + 版权头 + git 时间戳（0）＋ 软著登记（几百块，只为"万一"）④发布日再定形态。

### 6.13 【本场新增 · 待议 决策 44】处理回复时的协同：认人认岗卡 + 指认 tab +「AI 填、你按」

**老板原话**（2026-09-20）："最后那个我想自己处理回复的时候，我估计我自己会迷糊，这个候选人和某个岗位的关联，小猎应该如何帮我呢……我给小猎说'你看看回复页面，现在这个候选人的问题，我如何回答呢'，小猎给我建议了我复制粘贴就好了。现在我不是还要在 chat 页面和回复页面跳来跳去？要是我们把小猎做成目前类似 dsh 浏览器助手那样就好了，但是不知道有没必要。"

**诊断：两个痛点被混成一个** —— **真痛 = 认人认岗**（迷糊：这人是哪个岗的）；**只是烦 = 窗口切换**。

**能力现状（本场查实）**

| 谁 | 能直接读浏览器页面吗 | 依据 |
|---|---|---|
| **DSH 会话（`:3080`）** | ✅ **能**（`browser_snapshot` 等工具直接可用） | 本场实测 |
| **面板小猎（`:8501`）** | ❌ **不能直接读**，只能靠脚本当眼睛 | `framework_config.TOOL_PROFILES["bare"]` 只**关闭**工具行，**没有桥/浏览器工具那一行** |
| `reply_run.py` | ✅ 能（它自己用桥读） | 已实测：列表模式 30 条会话、`--deep` 读详情 |

**"认人认岗"的真实缺口（三条，全部查实）**
1. `greeted_candidates()` **只取"我们打过招呼的人"** ⇒ **主动投递的人根本不在里面**（而老板迷糊的正是主动投递，见 §2.6）；
2. 只按**单个 `job_code`** 查 ⇒ **没有跨岗反查**；
3. `mapping.json`（禾蛙↔猎聘映射）**尚未落地**（当前岗位目录实测无此文件）。

⇒ 缺口不是"浏览器助手"，而是**一张跨岗认人卡**：

```
【认人】程** · 某某公司 · 机械设计
【认岗】① 机械工程师（本单 hjobId=79866575）— 9/19 我们主动打招呼 ✅
        ② 后端设计工程师 — 在池子里，未打招呼
【历史】我们发过 2 条；他回过 1 条（今天 14:22）
【他最后说】"方便发一下岗位职责吗？"
【建议话术】……            [复制到剪贴板]
```

**四个档（按成本）**

| 档 | 做什么 | 成本 | 消掉什么 |

### 6.15 【本场更正 · 老板指正】那个浏览器助手是独立工作区插件：`C:\deepseek\dsh-browser`

**老板指正**："这个 dsh 浏览器助手，是 dsh 的一个插件，他的目录在 `C:\deepseek\dsh-browser`，里面有源码，我们这个桥当时也借鉴了它。"

**⚠️ 更正 §6.14**：我上一轮"它不是可挂载的 DSH 包"的结论**错了**。错因：我搜的是 DSH 主干工作树（`C:\deepseek\deepseek-harness`），而它在**另一个独立工作区**。**老板是对的。**

**它的真实身份（只读查实）**
- `dsh-browser` **v0.1.3 / MIT / 作者 Yuxiang Lin**；自述 = "Standalone dsh browser bridge and controlled-tab Chrome/Firefox extension workspace"。
- 两半：`packages/browser/bridge-browser`（宿主插件 **`@yuxianglin/dsh-bridge-browser` v0.0.4**）+ `extensions/dsh-browser`（Chrome/Firefox 扩展，**自带侧边栏，可直接对话**，会话落 `~/.dsh/browser-sessions`）。
- **它是标准 bundle patch 插件**：`dsh.bundle.patch → cordis.patch.yml`，内容是 **`- insert:` 一行**（不是 disable）：
  ```yaml
  - insert:
      - id: bridge-browser
        name: '@yuxianglin/dsh-bridge-browser'
        config: { token: !!js process.env.DSH_EXT_TOKEN, toolTimeoutMs: 90000, snapshotMaxChars: 32000, maxInteractiveItems: 60 }
  ```
- 注册方式按它自己的注释：**`dsh plugin --profile web add`**（⇒ **按 profile 注册**，与我们的 SDK 档同构）。

**能不能挂进 SDK 档？三个硬约束**
1. **它要"宿主 web server"**：peerDeps 含 `@deepseek-ai/dsh-host-webserver`，桥本体是**给扩展连的 WebSocket 服务**（`server.ts`/`host-api.ts`）。而我们的 SDK 档是 **headless**（`profile="sdk"`，无 web 宿主）⇒ **不是"加一行"就行**，缺的是承载它的宿主进程；
2. **版本差**：它 peer `@deepseek-ai/dsh-*@^0.1.2-rc.1`，我们的运行环境是 **0.1.5 系**。好消息：它用 `insert` 插行，**不依赖既有 row id**（不会因 row 改名而挂不上）；坏消息：宿主服务 API 若有漂移会在运行时报错 ⇒ **只有实测能定**；
3. **它有 client(web) 部分**（`dsh.client` + `platform: "web"`，注入 ui-slots/settings/locale）⇒ 完整形态就是"web 档 + 扩展 + 侧边栏"。

**⇒ 关键结论（确定度高）：两者定位不同，不是二选一。**

| | `dsh-browser`（插件） | 我们的 `bridge-agent`（桥） |
|---|---|---|
| 谁在用 | **模型**（`browser_*` 工具）+ 扩展侧边栏 | **脚本**（HTTP 任务队列 + 配方） |
| 载体 | dsh 宿主 web server + WS | 独立 HTTP 服务（`:8080`） |
| 同屏体验 | ✅ 扩展侧边栏（页面在左、对话在右） | ❌（要自己在浏览器里并排） |
| 归谁 | 别人的（MIT，可引） | **我们自己的** |

**据此三条路（按推荐度）**
- **主线**：面板 + **脚本当眼睛**（§6.14 方案不变）——它是"给脚本用"的形态，与面板小猎（SDK + `tool-pwsh`）天然匹配；
- **想要"页面同屏对话"的现成体验**：直接用 **`dsh-browser` 的扩展侧边栏**（**零开发**），但要给它配小猎人设（回到决策 36 的 preset）；
- **非要"注册进 SDK 项目"**：做一次**半小时挂载试验**（把包装进 `data\dsh_home\profiles\sdk` 的 workspace + 并 patch）。**试验目标是"确认它到底需要哪些宿主能力"**，而不是"一次挂上"——按约束 1，预期会卡在"SDK 档没有宿主 web server"。

### 6.18 【本场查实 · 补记】wails 扩展 vs 小猎跑腿：业务该放在插件里吗

**老板**："在 wails 项目中，浏览器插件具有部分业务功能，现在我们的小猎跑腿只是一个服务功能。"

**准确事实**：wails 扩展 6 文件（`extract.js` 14.1KB／`popup.js` 28.1KB／…），manifest 声明在猎聘/禾蛙页面完成"岗前分析、岗位采集、候选人采集与匹配"；但 **`extract.js` 第 3 行自己写着**："本文件**只做『页面判定 ＋ DOM 提取』，不内置任何业务/授权逻辑**"——业务规则在 Go 后端 API（`/api/candidates/capture`、`/api/candidates/match`、`/api/pool/capture`…）。⇒ 它带的是 **①页面判定 ②DOM 结构化提取 ③业务按钮入口**。我们的跑腿 popup **只有"状态 ＋ ⛔ 停止"**（无业务按钮）。

**真差别 ＝ 页面知识放在哪一层**：wails 硬编码在扩展（**改版要手工 rar 重装，无 `.crx`/`update_url`**）；我们在 Python 侧（`knowledge_config.json` ＋ `knowledge.py` ＋ 配方，且有 `verify_site` 锚点校验／`site_changed` 降级／视觉复核／经验沉淀）。
**⇒ 我们的"纯跑腿"不是弱，是"把最易变的东西放在最能改的地方"；不要为了像 wails 而把业务塞进扩展。**

**值得抄的四样**：①**页面判定做成一等动作**（`zlDetectPageType` → `{site,type}`；我们缺"页面类型"返回 ⇒ 桥加 `detect`）②"这一页能干什么"显式化（做进**面板"当前页面"区**，不做进 popup）③**老熟人回馈**（`existing=已在库`／`updated=已更新` ⇒ 嫁接进认人卡）④**批量详情页采集**编排。

### 6.19 【本场收敛 · 补记】壳搬进浏览器扩展：侧边栏 ＝ 壳 ＋ 眼睛（决策 36 的候选答案）

**分工原则**：**扩展只"抓"（通用结构化文本），Python 侧"判定与解析"**（保住配方资产，改版不重装）。
**闸门**：复制 ✅｜填文本 ✅（可逆）｜**发送 ❌ 永不**。
**连带**：`m3_chat` 降为执行台；"面板看不见页面"消失；决策 44"面板嵌当前页面区"降级；"三个半身"消失。

### 6.21 【本场讨论 · 补记】7×24：先把「全自动」和「自主」分开（细化 决策 37）

- **全自动** ＝"没人也照跑"（流程的确定性执行）；失败模样 ＝ **流程走歪了没人知道**。
- **自主** ＝"没人叫也在动"（决定权在它）；失败模样 ＝ **它在替你经营**（`重走复盘` 原话：小猎若自己决定先打哪个岗，"就在替老板做经营决策"）。

| | 不自主 | 自主 |
|---|---|---|
| **全自动** | 你按一下它跑完整条流水线（`auto_job.py` 一条龙 ＝ 现状） | 自己决定跑哪个岗哪一步再自动跑（**危险区**） |
| **非全自动** | 你一步步按（面板步骤制） | **它主动开口**（他回了／该跟了／岗停了）← **最被忽略、最适合先做** |

**猎头业务里"自主"的天花板低**：①不可逆必须留闸门 ⇒ 动手不能自主 ②夜里平台没窗口 ⇒ 需要登录态的动作不能自主 ③**额度怎么在岗间分 ＝ 经营决策** ⇒ 分配不能自主。
**⇒ 7×24 ＝"我睡觉它值班，我醒来它交班"**：值班只做**看/想/写**（复盘、排序、起草、查资料、写 journal 与日报）。

**自主阶梯（＝决策 23 放手阶梯接到时间维度）**：L0 被动执行｜**L1 主动提示 ✅先做**｜**L2 主动准备 ✅先做**｜L3 按已确认方案自动（可到）｜**L4 自主决定做什么 ❌不做**。
**"全自动"自己的两个难点**：**触发** ＋ **异常兜底**；共同地基 ＝ **journal**（第三次印证）。
**降本判断**：**很多"7×24 的价值"可用"开工即就绪"拿到**——不需要真的无人值守跑，只要**你早上打开它时那一屏已经准备好**（触发点＝你打开它）。先做这个，再谈定时器与无头。

### 6.22 【本场讨论】老板给的四个真实场景 ＝ 一根链条的四段

**场景**：①"这有一个新岗，你按 **A 计划**作完吧"（A ＝ 岗位分析**不问 PM** → 采集 → 匹配 → 打招呼，**不管回复**）②"这里面有 **10 个岗位**，你按 **B 计划**走吧"③"我上来就说 **开工**"④"我问，**这一周干的如何**？"

| # | 自主级别 | 底层要求 | 风险 |
|---|---|---|---|
| 1 | **L3** 单岗 | 方案可执行 ＋ 触发（你发起）＋ 异常兜底 | 中（跑错＝白采＋浪费额度） |
| 2 | **L3 批量 ＋ 排序/额度分配** | 1 的一切 ＋ **顺序规则 ＋ 额度分配 ＋ 失败隔离** | **高**（额度稀缺且不可逆） |
| 3 | **L2→L3** | 状态盘点 ＋ **排序规则（你定）** ＋ 今日计划 | 高（规矩没定 ＝ 替你经营） |
| 4 | **L2 只读** | **journal ＋ 台账**（现在答不了） | 零 |

**三条判断**
1. **场景 4 最便宜，但它是 1/2/3 的安全网**（journal 是"走歪了没人知道"的唯一解药）⇒ **先做 4 不是为了 4**。
2. **场景 2 是"经营决策"的分水岭**：B 计划**写了**"顺序 ＋ 额度怎么分" ⇒ L3 安全；**没写** ⇒ 小猎必须自己定 ⇒ **L4 越界**。⇒ **"B 计划"的价值 ＝ 把你脑子里的排序规则外化成文档，只有你能做**；场景 2 的前置条件 ＝ 先写 B 计划（哪怕三条规则）。
3. **场景 3"开工"不是新能力**，＝ 去掉"对象指定"的 A/B；正确形态：**先给今日建议（一屏）→ 你点头/改口 → 再按 A 或 B 跑**；**不要让"开工"＝自己开跑**。

**四段共用一套地基**：①**方案库**（A/B 能被点名、能执行、能汇报"走到第 3 步"）②**journal** ③**状态盘点**（每岗停在哪／池子多少／打过多少／谁回了）④**闸门清单**。
**⇒ 强收敛**：这四个场景把**决策 22 第三层「岗型方案层」**（`重走复盘` §175 原话："按方案 B 执行，我去喝酒"里的那个 B **从未存在**）**从"一直没做"变成马上要做的刚需**。
**观察**：A 计划带**参数**（"不问 PM"）和**停止点**（"不管回复"）⇒ **方案形状 ＝ 步骤 ＋ 参数 ＋ 停止点**。

**⚠️ 老板确认（2026-09-20）**："A 计划现在还是讨论的内容，从来没有落地啊，我们不是才把这几个环节测试完了吗。"
⇒ **A/B 计划目前不存在**（只是口头概念）；**零件（①分析／②采集／③评估／④打招呼／⑤查看回复）已逐个测通**。
⇒ **落地 A 计划不是造新东西，是给已有零件加一层"方案壳"**：步骤 ＋ 参数 ＋ 停止点 ＋ 每步产物 ＋ 每步闸门 ＋ 失败停在哪。
⇒ **三个真实缺口**（"测通了"≠"能串起来"）：①**参数化**（现在参数在命令行/写死，要改成"从方案读"）②**断点续跑**（跑到一半失败，下次从哪继续）③**进度可见**（"这单跑到哪了"现在要问人/翻文件）。
⇒ **最便宜的"进度"来源（不用等 journal）**：**每一步都有落盘产物**（`data/chat/<job>/` 里 `jd.txt`／`job.db`／`job_profile.json`／`state.json`／`reports/`）⇒ "方案步骤 ↔ 产物文件"的映射即可推算进度。

### 6.23 【本场讨论】工作页面：`:3080` ≠ 工作页面；wails 的页面借"对象"不借"实现"

### 6.25 【本场查实 · 修正一条】"一个岗位持续完成自动化"：Streamlit 不适合当引擎，**但引擎已经存在**

**老板问**："如果做起一个岗位持续完成自动化，Streamlit 这个平台适合吗？"

**查实两条（读源码）**
1. **面板跑脚本的方式**（`m3_chat.py:2154 run_script`）：`subprocess.run(cmd, ..., capture_output=True, timeout=600)` —— **同步阻塞**。注释写"**不占面板线程**"**不准确**：它占住该会话的脚本线程，**界面停在那一步、跑完才出结果**（`capture_output` 意味着**无实时进度**）；且 **`timeout=600`（10 分钟）** ⇒ 采集/评估若超 10 分钟会抛 `TimeoutExpired`，被兜底成一句"跑 xx 出错"。
2. **"一条龙"引擎已经存在**：`auto_job.py`（746 行）—— `ALL_STEPS = ["analyze","plan","collect","eval","detail","greet","html"]`；带 **②采集计划闸门**（停下属确认，`--yes` 跳过）｜**④详情深采风控点**（默认再问）｜**打招呼＝永远人工**（只产清单 HTML）｜**幂等续跑（缺啥补啥）**｜**`--step` 可多次（按步点名重跑）**｜`--dry-run`｜限速保险丝｜数据/展示分离。

**⇒ 结论**
- **Streamlit 适合当"操作台/仪表盘"，不适合当"跑单引擎"**（硬限制：同步阻塞／无实时进度／无队列与并发／内存态不落盘）。**但你不需要它当引擎——引擎早就是 `auto_job.py`。**
- **真正的缺口是"接线"，不是"选平台"**：面板不该 `subprocess.run` 等结果，应该**投任务 + 轮询 `state.json`/产物**；闸门应从"终端按 y"变成"**面板上点确认**"。
- ⚠️ **顺带揭出一个真要验的问题**：从面板调 `auto_job.py` 时，它的闸门用 `input()` 等确认，而 `subprocess.run` 的 **stdin 不是终端** ⇒ 很可能卡住/EOF。**下一场先验这一条**（便宜，但决定"从面板跑一条龙"能不能用）。
- **⇒ "A 计划"的真相**：**A 计划 ≈ `auto_job.py` ＋ 一张纸**。纸负责**点名／参数／停止点／进度口径**；引擎负责跑。
- 🔧 **修正我上一轮的说法**：我说 7×24"需要一个常驻 runner"——**修正**：**不需要常驻 runner**。`auto_job.py --yes` **已经是无人值守形态**；7×24 缺的只是 ①**触发**（定时器/任务计划）②**落点**（日报）③**记录**（journal）。

### 6.26 【本场讨论】"要是用 Vue 呢"：Vue 不是引擎，是壳；什么时候才值得上

**关键前提（§6.25 已定）**：引擎（`auto_job.py`）与界面**已解耦**，缺口是"接线"不是"选平台" ⇒ **换不换 Vue，与"一个岗持续自动化"无关**，只影响**手感与展示**。

**Vue 能买到的**
1. **任意布局**（三栏／卡片流／悬浮／侧边栏），摆脱 Streamlit 的 rerun 模型；
2. **真异步**：前端状态与后端任务解耦 ⇒ 长任务天然可行（后端跑、前端轮询/推送）；
3. **细交互**：一键复制、快捷键、行内编辑、实时进度；
4. **可打包成静态产物**：Vite 构建 → 静态文件，**py 起本地 HTTP 就能供**（**不需要 node 运行时**，只在构建期需要）⇒ 与"纯 py 自足"**不冲突**。

**Vue 要付的**
1. **一个前端工程 + 构建链**（node/pnpm/vite，产物要管）；
2. **必须新造后端 API 层**：Streamlit 时代 UI 直接调 py 函数；Vue 必须走 HTTP/WS ⇒ py 侧要新建一组 API（读 state/产物、发指令、跑任务、看日志）；
3. **对话流要自己做**（SSE/WS 流式渲染）—— **这是最重的一块**，也是 Streamlit 白送的；
4. **两套状态的风险**：前端状态 vs `state.json` ⇒ 必须立"**盘上为准**"，否则又是两份真相；
5. **长期维护**：一个人 + 一个 AI 维护两套技术栈。

**⚠️ wails 的教训（不是 Vue 有毒）**：它就是 **Vue 3 + Element Plus + 12 视图**的后台；结果"多页面 UI 查询"逼出 **db 为主**，被**决策 26 判掉**（"db 的 UI 查询场景没了"）。⇒ **危险的不是 Vue，是"多页后台"会把架构拉回 db 中心。**

**判据：什么时候才值得上 Vue**
- **触发条件**：出现一个 **Streamlit 做不到的具体交互**。目前两个候选都**不成立**：
  - "一键复制话术" ⇒ **Streamlit 代码块自带**（§6.20 步①）；
  - "与页面同屏" ⇒ 那是**浏览器扩展的前端**（本来就要写 HTML/JS），**与 Vue 无关**。
- **时机**：**"同事版"真要交付时**（需求稳定了才值得投 UI 工程）。现在投 ＝ 为一个还在变的需求写前端。

**⇒ 我推荐的折中（零新工程）：把"渲染"与"交互"分开**
- **重的展示**（池子表格、报告、今日一屏）→ **本地模板渲染 HTML**（`report_html.py` 那条路，0 token、无 node）；
- **轻的交互**（按钮、对话、闸门确认）→ 留在 Streamlit；
- 将来真要上 Vue：**HTML 模板 → 组件，后端逻辑不动**，升级路径不堵。

### 6.27 【本场讨论】"一天的流程"扛不扛得住：不是 UI 的问题

**老板场景**：A 计划定好后，小猎自动分析 → 出采集计划 → 采集 → 匹配 → 出打招呼计划 → 打招呼，"**这个流程可能他自己干，需要一天时间吧，我担心 Streamlit 能否抗住**"；另有场景 B："再选一个岗位，说'**你只做分析；如果你看没人用浏览器，你也可以采集**'"；并问会不会用到**子 agent / session id**（"先不考虑"），自己猜"**GUI 用 PySide 估计可以吧**"。

**① 关键重构：** "一天"**不是"一次运行 24 小时"**，而是**分散在一天里的许多短动作 + 长等待**。
等待来自：**人闸门**（采集计划确认、打招呼人工）＋ **平台额度**（打招呼 50/天、查看量 100/天）。⇒ **它天生就不该由一个 UI 连续承担。任何 UI 都扛不住"一次挂一天"——PySide 也一样。**

**② Streamlit 的真实边界（机制层）**
| 事实 | 后果 |
|---|---|
| 每个会话一个脚本线程、每次交互从头 rerun | 按钮回调里同步跑长任务 ⇒ **该会话界面卡死**，且不能点别的 |
| `run_script` = `subprocess.run(timeout=600)` | **10 分钟硬上限**；`capture_output` ⇒ 无实时进度 |
| `session_state` 不落盘 | 内存态随会话消失（**但真状态在 `state.json` ✅**） |
| 关标签/刷新 | 那一轮脚本的**输出与上下文丢**（任务本身可能仍跑完）—— **只要产物落盘，结论不丢** |

**③ PySide 的真实优势与代价**
- **优势**：①**能常驻**（顺便当调度宿主，这是 Streamlit 没有的）②UI 与任务同进程，状态不易丢 ③打包 exe 分发给同事更自然。
- **代价**：**UI 开发成本比 Streamlit 高一个量级**（控件/布局/表格/流式对话渲染全自己写）；一个人 + 一个 AI 维护两套技术栈。

**④ 结论表：能不能"扛住"取决于任务跑在哪**
| 任务形态 | Streamlit | PySide | 正确做法 |
|---|---|---|---|
| 分钟级动作 | ✅（界面卡那几分钟） | ✅（配线程） | 外部进程 + 状态文件 |
| 十几分钟～小时级 | ❌（10 分钟上限 + 卡死） | ✅（QThread/QProcess） | 外部进程 |
| **一天（含闸门与额度等待）** | ❌ | ❌ **同样不该** | **引擎 + 触发器 + 状态文件** |
| 多岗并行 + 资源互斥 | ❌ | ❌ | **调度器（队列 + 锁）** |

**⑤ 场景 B 的判断（重要）**：**"多岗并行 + 条件动作（没人用浏览器才去采集）"是调度问题，不是智能问题。**
- 正确形态 ＝ **一个脑子 + 一个队列 + 资源锁**（浏览器是**排他资源**）；
- ⚠️ **不该用子 agent 解决** —— 多 agent ＝ **多份真相/多个调度大脑**，与"一个脑子 + 多个壳"铁律直接冲突（决策 36 §3.4）。

**⑥ 要补的三样（与 §6.25 一致）**：①**投递**（面板不再同步等，立即返回）②**触发器**（先 Windows 任务计划；要"随时投任务"再常驻）③**调度器**（多岗 + 资源锁）。

**⑦ PySide 的定位**：留作"**同事版 / 常驻值班宿主**"的候选，等需求稳定再评估（判据同 §6.26）。**现在不必换 UI。**

### 6.28 【本场口径变更 · 决策 46】闸门从「按动作类型」改为「按置信度 ＋ 极少数硬边界」

**老板口径（2026-09-20）**："我们原来都讨论过这些规定啊、纪律啊，都是我们最初的设计——必须真人打招呼啊、必须真人回复啊，**我们早都说放弃了这些规定了，咋现在还操心这个呢**。我就是想**小猎吃不准的时候，暂停问问我**。现在我们俩不是也是这样吗？"

⇒ **口径变更（重要）**：废止"按**动作类型**设闸门"（打招呼/回复/微信/电话/谈薪资＝永远人工），改为"按**置信度**设闸门"：**吃不准就暂停问，吃得准就干**。
⇒ ⚠️ **随之需要一轮统一修订**：`授权矩阵`／`工作模式·备忘`／开工书 §2.6 等处仍写着旧口径（"微信/电话/谈薪资永远人工""打招呼必须人工"）——**不修订的话，未来的我会照旧铁律办事**。（这本身也印证：口径散在多份文档里，松绑时会变成负担。）

**但要补两条极小的硬边界（不靠它自评）**
| 边界 | 为什么不能交给"它吃不吃得准" |
|---|---|
| **花钱**（额度／API 成本） | 额度是**可耗尽的稀缺资源**，判断对了也可能不该花 |
| **以公司名义对外承诺**（薪资／offer／客户承诺） | 后果**由公司承担**，不是"它确定"就能做 |

其余（**含打招呼、回复、采集、发岗文字**）**全部交给置信度**。
**另加一条机制**：**不可逆动作 ＝ 更高阈值 ＋ 必须留痕**（不是"必须问人"，而是"必须有依据链、可回溯"）。

**⚠️ 一个必须说的技术事实（关于"吃不准"）**：**"吃不准"是模型的自评，而 LLM 的置信度校准很差——它最自信的时候可能最错。** ⇒ 纯置信度闸门会**漏报**。所以真正兜底的不是它的自评，而是**可观察性**（下条）。

**关键交易：松闸门 ⇔ 必须配可观察性**
我们现在俩能这样干，是因为**在对话里，你随时看得见我在干什么**。无人值守时，那个"看得见"必须由 **journal ＋ 每日交班**替代。
⇒ **journal 不只是"地基之一"，它是"松闸门的配套条件"**：**闸门松开多少，journal 就得有多细。**

**老板的第二问与回答**："假如我给你一个任务，你自己决策、自己调用本地代码/外部插件，**你能持续干一个月不**？（不考虑 token）"
- **能**（今天就在做：自己决策、自己调本地代码与插件、吃不准就问、出错自己修）；
- **但"一个月"的障碍不是 token、不是智力，是四个记忆与状态问题**：①**会话寿命**（上下文会满、会压缩，细节会丢）②**跨会话重建**（每次新会话我得靠读文档重新变成小猎）③**状态必须落盘**（否则换一天/换一个我接不上）④**卡住要能喊人**（卡在验证码/改版/弹窗上，没人看＝静默耗一天）；
- ⇒ **"一个月"成立的四个条件**：**①方案纸 ②状态与日志落盘 ③卡住就喊（推送出口）④每天一次交班（你看一眼）**；
- **诚实说我的弱点**：**我会"自信地做错"**（尤其在我以为自己理解了口径的时候）。所以"吃不准就问"这条**对我自己不够可靠**——真正兜住我的是**你每天看一眼 ＋ 我留下可追溯的痕迹**。这不是谦虚，是 LLM 的已知特性。
⇒ **结论：我可以承担"值班"，但"每天一次交班"必须保留**（成本极低、收益极高）。这也正是"早上那一屏"的真正价值——**不是给我看，是给你自己一个 30 秒的保险。**

### 6.29 【本场讨论】"15 个对话各挂一个长任务，来回切着看"是否可行？

**老板问**："我们现在大概开了 15 个对话了，我要是分别在 15 个对话中安排了长时间、持久的任务，我来回切换查看进度，是否可行？"

**查证（DSH 侧，读文档）**
- **并发会话是被支持的场景**：`docs/subsystems/sandbox.md` 明确 "This permits **concurrent sessions**, consumers, and one-shot escalated retries…"；每个会话 ＝ 各自独立的 live Agent。
- **同一会话内轮次串行**：agent driver 的 `running` 是"**整个驱动器的排空区间，可能跨越连续的排队轮次**"（`docs/subsystems/core.zh.md`）；live agent 忙碌时并发操作会被拒（**`session/agent-busy`**，`docs/api-gateway.md`）。
- ⇒ **技术结论：可以开 15 个会话各自跑**。⚠️【未实测】我读的是机制文档，**没实测 15 个同时跑的真实表现**（并发上限、内存/进程开销未验）。

**真正卡住的不是 DSH，是三类"排他资源"（都在你这边）**
| 资源 | 事实 | 后果 |
|---|---|---|
| **浏览器／扩展／桥** | `dsh-browser` README：**单活动连接**、绑定**一个**受控标签页；你的桥也是"一个任务队列 ＋ 一个扩展" | **15 个会话不能同时用浏览器** ⇒ 抢浏览器必须**串行** |
| **平台账号额度** | 打招呼 **50/天**、查看量 **100/天**，是**账号级**稀缺资源 | **跟开几个会话无关**——开 15 个也还是 50 |
| **同一工作区文件** | 多个会话同时写 `data/`、同一个 git 工作区 | **并发写冲突／覆盖**（最容易被忽视的一种） |

**而"来回切换查看进度"这件事本身不成立**：**进度不在对话里，在盘上**（`state.json` ＋ 产物）。
切到另一个会话，你看到的多半是"**上一回合已结束、它在那儿等着**"，而不是一条进度条。**15 个会话 ≠ 15 个进度条。**

**⇒ 正确形态（与 §6.25／§6.27 一致）：任务不放会话里。**
- 会话 ＝ **"说话的地方"**；任务 ＝ **"引擎 ＋ 状态文件"**；
- **一个会话（或一屏）看全局**：15 个岗位 → **15 行状态**（数据已在 `state.json`）；
- **引擎在盘上跑**（`auto_job.py` 幂等 ＋ 触发器）；
- **会话只在"要我陪你想"时开**（讨论／决策／救急）。

**⇒ 老板最早的设想"一个对话一个岗位"要分场景看**：
- **"讨论／决策"场景成立**（就像我们现在这样）；
- **"跑流程"场景是错的载体**（会话有上下文成本、会压缩、会丢，而且它不是进度条）。

**③ 本场新查实：三个"现在突然对口"的原生能力（因为决策 46 改了闸门口径）**
| 能力 | 是什么 | 对口哪个需求 |
|---|---|---|
| **`ctx.approval`（`dsh-user-approval`）** | 每次问"这个动作能不能过"：按会话 `ask`/`never` 策略、**fail-closed**（除非 `allowed-once` 一律拒）、**审计事件对 `approval/asked` ＋ `approval/decided`** | **决策 46"吃不准就问"** —— **不用自己造闸门**；且**自带审计**，正好补上"松闸门必须配可观察性" |
| **plan mode（`exit_plan_mode`）** | 呈交一份完整 markdown 计划，经 **user-questions seam** 评审，批准返回 `{approved:true}`；不批准则带反馈重来 | **"A 计划先给你看、你点头再执行"** ⇒ **方案纸的天然载体**（且它本来就在工具面里，被我们关了） |
| **`tools/pre-execute` 策略** | 工具派发前 allow／deny／**ask**，前置策略可拦 | **"闸门清单"的落地位置**（按工具配闸门） |

**④ 我的建议**
- **继续关**：`workflow`／`ralph`／`todo`／`tool-web`（省钱 ＋ 防跑偏）；
- **值得开**：①**plan mode**（＝方案纸）②**approval ＋ user-questions**（＝吃不准就问，带审计）③**skill**（把 `data/prompts/*.txt` 手册变成**按需加载、可版本管理、别人能加**的插槽）；
- **要验的老尾巴**：**subagent provider**（"挂载配置未验"；真分身需 `dsh-subagent-dsh-sdk`）；
- **不急**：MCP（每轮收租）、插件（作废风险）。
