# 授权矩阵（M3 信任演进 · 动作分级授权）

> 版本：v0.1 草案 ｜ 日期：2026-09-01 ｜ 状态：待用户验收补充后定稿
> 原则（SDK 技术评估 §4）：**可逆动作全自主，不可逆动作留闸门**
> 来源：继承 `参考代码\lietou-agent\docs\blueprint.md` 已验证边界（打招呼/微信/电话留人工 + 额度分配 + 优先级报告）＋ 平台约束（猎聘 50 打招呼/天、查看量风控）
> 用途：M2 挂采集、M3 做闸门时照此配工具权限与汇报形态

## 1. 动作分级表

### 阶段 1 · 分析评估类（当前已验证 ✅）

| 动作 | 可逆性 | 授权级别 | 闸门/汇报形态 |
|---|---|---|---|
| 读 JD / 岗前分析 / 转关键字 | 完全可逆 | **全自主** | 岗前分析报告（M1.1 已验证） |
| 候选人池评估 / 逐人匹配评分 | 完全可逆（本地） | **全自主** | 池子评估报告（M2a 已验证） |
| 寻访关键词 / 话术草稿生成 | 完全可逆 | **全自主** | 报告内附，不直接外发 |

### 阶段 2 · 采集沟通类（M2 待账号审核，落地时照此配）

| 动作 | 可逆性 | 授权级别 | 闸门/汇报形态 |
|---|---|---|---|
| 猎聘搜索 / 翻页 / 筛选 | 消耗查看统计 | 自主，**限量限速**（分时段，像真人） | 采集批次报告 |
| 查看候选人简历详情 | 消耗查看统计（**风控点**） | 自主，限量限速 | 池子报告 |
| 简历采集入池（本地库） | 可逆 | **全自主** | 池子报告（入 SQLite 业务库） |
| 收藏 / 关注候选人 | 轻微但触发风控 | 谨慎：默认不做，任务要求才做 | 报告说明 |
| **打招呼 / 发消息**（50/天） | **不可逆**（消耗名额+暴露账号） | ⏸ **讨论中**（2026-09-06 老板调整：可自动化，见 §8）；当前仍只生成待打招呼清单+话术 | 清单按优先级排好，老板照着打（lietou-agent 已验证形态） |
| 下载联系方式 | 消耗资源（部分收费） | 🔴 **闸门：列清单，老板点** | 同上 |
| **约面试 / 沟通安排** | 不可逆（对外） | 🔴 **闸门：给建议，老板执行** | 建议清单 |
| **推荐候选人给客户** | 不可逆（对外承诺，伤信誉） | 🔴 **闸门：推荐报告，老板确认后发** | 待拍板清单 |

### 阶段 3 · 跟进类（远期，永远人工）

| 动作 | 可逆性 | 授权级别 | 说明 |
|---|---|---|---|
| 微信 / 电话沟通 | 不可逆（对外+信任） | 🔴 **永远人工** | 系统只记事件（candidate_events，参考 wails 表） |
| 谈薪资 / 做承诺 | 不可逆 | 🔴 **永远人工** | — |

## 2. 闸门的两种实现（都做）

1. **执行层闸门 = 能力即闸门（最硬）**：agent 工具按 profile 挂载控制——只挂采集/分析工具，**不挂打招呼/发消息工具**。物理上做不到越权。
2. **输出层闸门 = 待拍板清单（日常）**：agent 报告带"我建议这么做，等你点头"段；老板确认后由人执行（或老板点按钮触发）。

## 3. 额度管理（50 打招呼/天 · 共享池）

- 一个账号挂多岗共享 50 次/天额度（lietou-agent dispatcher 已验证：加权得分排全局队 + 防重复认领，可复用）
- 报告里排好优先级顺序，老板照着打即可（第一阶段形态）
- 查看量风控教训（lietou-agent HANDOFF-P6）：多账号 ≠ 多员工，账号池（一员工切多账号）更轻量；采集必须限量限速像真人
- **限速已落地（2026-09-01；2026-09-05 拍板放宽策略）**：`bestagent\quota.py`（记账+限额检查+随机延迟），`collect_liepin.py` 已集成（每轮搜索前查额度、轮间随机延迟、每轮记账）；**限额策略（老板 2026-09-05 拍板）**：平台只统计「查看简历数/沟通/联系方式/云电话」，**不统计搜索次数**（几万查看简历数才是异常信号）→ 搜索上限 20→**80/天**（降级为防失控熔断，不再是日常约束）、提取 200→**500/天**、轮间延迟 5-15→**8-20 秒**（模拟真人节奏的核心，保留且略放宽），并**预埋「查看简历数（打开详情页）」日上限 100**——将来详情深采步骤接入即自动生效（列表页采集不开详情页，安全）；配置在 `bestagent\data\usage\quota_config.json`（2026-09-05 已建；不存在则用 quota.py 内置默认，已同步同值）；`--no-quota` 跳过（调试用）

## 4. 汇报粒度 = 信任刻度

| 阶段 | 汇报频率 |
|---|---|
| 初期 | 每步都汇报（分析完/筛完/评完） |
| 中期 | 只汇报关键节点（挖到优质候选、触发闸门） |
| 后期 | 只报异常（放手策略） |

## 5. 补充规则

- 信息不足必提问（硬闸门）：JD 缺关键字段（佣金/薪资）时不许猜，停下来问老板。
- 数据校验闸门：池子评估必做 data_valid 校验（M2a 已验证 agent 能自主发现重复/无效采集）。

## 7. M3 设计讨论提纲（2026-09-01 深夜新增，待新对话专门讨论）

> 定位：新开一个"设计讨论"对话（只讨论 + 落决策记录表，不写实施代码）。
> 背景：框架 v1.0 已交付（"做"的加速器已就位）；M3 信任演进 = "想"的产品化，动手前必须先想清楚（决策 10：汇报机制=产品核心设计点）。

**待拍板 5 个未决点：**

1. **汇报粒度切换机制**：初期"每步汇报"→ 中期"关键节点"→ 后期"只报异常"——"每步/关键节点"具体定义？**切换条件**是什么（信任积累次数？老板手动切？还是按岗自动？）
2. **闸门等待策略**：触发待拍板清单后，agent 是**停住等**老板确认，还是**继续干其他可逆活**（如先补采、先评估别的池子）？
3. **放手策略信号**：什么可量化指标说明"可以放手"（如连续 N 个岗位汇报采纳率 > X%？或按动作类型分别定）？
4. **授权矩阵验收**：①分级对不对（重点：查看简历详情=自主/谨慎？）②平台动作有无遗漏（屏蔽/拉黑/举报/收藏等）③限额数字拍板（当前 20 搜索/200 提取/天 是试跑默认还是正式值）
5. **信任破坏与恢复**：agent 粉饰/漏报/判断失误后，信任如何降级、如何恢复（回滚机制？强制回到"每步汇报"？）

**讨论产出**：每条 → 决策记录（结论 + 理由）→ 回填本矩阵定稿 + 更新 PROGRESS 决策记录表。

### 2026-09 设计对话处理结果（v0.1 试用默认，边用边改；跑 N 单后回填定稿）

> 老板拍板：5 点暂无真实数据不好定死 → 先按下列试用默认落地界面与行为，用几单有手感后再回来拍板。步骤制模型详见 PROGRESS「M3 设计讨论记录」。

1. **汇报粒度切换机制** → 采纳"**步骤制**"（每业务步骤完成 → 交报告 → 老板介入 → 下一步），取代 §4 三阶段作为初始模型；信任演进暂缓：**默认每步都停**，跑几单后试点放开"步骤② 候选人评估"（可逆、本地、风险最低）。
2. **闸门等待策略** → 默认**停住等老板**；报告附一句"等待期间我可顺手做 X（可逆活）"，老板批准才去。宁可慢，不自作主张。
3. **放手策略信号** → 先定机制不定数字：每个步骤报告记"**采纳 / 纠错**"两笔账（= 成长数据），真实跑 5–10 单后填阈值（如连续 N 单 0 纠错 → 该步骤免停）。
4. **授权矩阵验收** → ①分级维持现状（"查看简历详情 = 自主限量"并入 quota 账本）；②补漏：**屏蔽 / 拉黑 / 举报 = 永远人工，agent 不做**（猎头非企业招聘方，用不上）；③限额 **20 搜索 / 200 提取/天 = 正式默认**（quota_config.json 可调，不够再调）。**【2026-09-05 修订，见 §3】**：搜索次数非平台红线（平台只统计查看简历数/沟通等），上限放宽至 80/天仅防失控；提取 500/天；轮间 8-20s；**风控主线 = 查看简历数（打开详情页），日上限 100 预埋**——列表采集不开详情页安全。
5. **信任破坏与恢复** → 原则："**判断错不罚，不诚实必罚**"。判断失误（如实汇报但评错）= 正常纠错不降级；粉饰 / 漏报 = 强制回"每步汇报" + 该岗位相关步骤重跑 + 记入岗位档案；连续 3 单诚实汇报后恢复原档。正面样板：m3_auto_run 如实报"池子差"。

## 8. 打招呼自动化 · 讨论状态（2026-09-06 老板调整）

> 老板改口：日常真正的麻烦点在**沟通跟进**（打招呼→回复→转微信），而非发岗；自动打招呼 / 自动处理回复技术上不难，值得讨论。故把 §1 阶段2 里"打招呼 = 🔴 永远闸门"改为 **⏸ 讨论中**（本文档 §1 行已改）。微信/电话段（阶段3）**维持永远人工，未改**。

- **改动范围（本次）**：仅"打招呼 / 发消息"授权级别改 ⏸ 讨论中；下载联系方式、约面试/沟通安排、推荐候选人给客户等其余 🔴 闸门行**未动**。
- **事实记录（老板 2026-09-06 提供）**：① 平台允许 30 个岗位同时在线的上限；② 老板日常大部分工作是**不带岗位信息直接开聊**；③ **大量沟通最终转到微信** → 平台侧自动化的天花板 = "第一公里"（初次接触+初轮应答），微信侧才是主战场但 AI 未接入（机器人项目暂停；微信自动回复另有合规/账号风险），故需"平台初轮自动 + 转微信后人工"的分工设计。
- **讨论点（未决，另行设计）**：① 自动打招呼（≤50/天额度内脚本驱动）的放行条件与话术质量门；② 自动处理回复的范围边界——只答可答问题（澄清/核实/约时间意向），**谈薪资/面试承诺/联系方式索取仍留人工**；③ 平台沟通记录如何自动归集（candidate_events / 会话导出），让人工接手微信时上下文不断；④ 与成长账/纠错机制如何衔接（话术被候选人无视/拒绝 = 纠错信号）。
- **维持不变的硬边界**：微信 / 电话沟通、谈薪资 / 做承诺 = 🔴 永远人工（§1 阶段3）；下载联系方式、约面试、推荐客户仍 🔴 闸门。
