## 1. 目的声明（动手前先对齐）

**要解决的事**：让"一次正式采集"变成一条**确定的、可复现的、能自己知道什么时候该停**的流水线——
输进去的是岗位 + 关键字，跑出来的是**本岗库里一批过了本地粗筛的候选人**，以及一份**说清楚每一步发生了什么的本地报告**。
**不解决的事**：不判断"这个人到底合不合适"（那是③匹配层，本轮不碰）。

**为什么现在做**：现状是"每个关键字只抓首页 30 人、抓完就完"——三个已知窟窿（报告 §2.4-c）：
①**0 处翻页**；②**不做跳过已采**（重跑重复抓、白烧额度）；③抓完只落一个大 JSON，**没有人知道哪一页开始跑偏了**。

**做完之后老板能拿到什么**：点一次「②正式采集」→ 本岗目录里多一个 `job.db`（这批人的底账）+ 一份采集过程网页
（每页命中多少、通过率多少、停在第几页、为什么停）。**这一步 0 token**（全是本地规则），花的只有猎聘动作次数。

## 2. 一次正式采集，长什么样（老板视角 8 步）

用 172253（电气设计工程师，南京）当例子，假设关键字就用体检跑出来的那两条。

| 步 | 发生什么 | 谁在动手 | 花钱吗 |
|---|---|---|---|
| **0** | 老板点「②正式采集」→ 出了计划 → 老板说"按计划跑" | 老板 | 0 |
| **1** | 脚本发现猎聘 tab（找不到就报错停下，**不猜**） | 本地 | 0 |
| **2** | **背后点猎聘**：打开找简历条件页 → 点「清空筛选条件」 | 🔴 浏览器 | 0 token，算 1 次页面动作 |
| **3** | **背后点猎聘**：按配方表设关键字 + 条件（每个条件**强制校验**，没生效就硬失败停下） | 🔴 浏览器 | 同上 |
| **4** | **背后点猎聘**：点「搜 索」→ 读页面上「共N位人选」（N = 这个关键字的池子总量，**免费体检读数**） | 🔴 浏览器 | +1 次搜索 |
| **5** | 读第 1 页 30 张卡片（`extract`：姓名/年龄/年限/学历/城市/期望/公司/职位/学校/`res_id_encode`）→ **本地粗筛打分** → 过线的 **upsert 进本岗库**（顺带把这页原文丢进 `pool_samples` 留底） | 本地 | 0 |

## 3. 翻页怎么翻（技术方案）

| 项 | 方案 | 把握度 |
|---|---|---|
| 点哪个东西 | **文本定位点「下一页」**（走桥现成的 `click_by_text`）；老板老代码用的是 `li.ant-pagination-next`，同一套 Ant Design 分页控件——**配方表里早写了"分页（li 编号/下一页）"** | 【已查证】控件存在；【未验】"下一页"这三个字能不能被 `click_by_text` 找到 |
| 为什么不用 `li.ant-pagination-next` 选择器 | 桥的快照**只收录可点元素**（a/button/input/role=button…），分页 `li` **不在快照编号表里**（【已查证】报告 §6.2）。真想按选择器点，得给桥**新加动作**（扩 1 个函数 + 动作注册 1 行 + **老板手动重载一次扩展**）——能不做就不做 | — |
| 怎么确认翻成功 | **比对"第一行人的 `res_id_encode`"**：翻页前记下来，翻完变了 = 成功；没变 = 没翻动 | 【已查证】`res_id_encode` 稳定可取（`fields.res_id_encode`，§6.2）；老代码就是这么判的 |
| 怎么知道到头了 | ①点「下一页」找不到该文本 / ②点完第一行的人没变 / ③页数达到算出来的总页数 / ④命中总数只有一页（<30 人）——**四选一命中就停，并如实写停的原因** | — |
| 翻页后怎么等 | 点完**等 8 秒**（照抄配方表实测：即点即搜 8 秒才刷对，2.5 秒不够）+ **轮间随机 8~20 秒**（`quota.delay()`，防账号风控） | 【已实测】出处：`page_recipes.json` behaviors |
| 会不会漏页 | **必须每页都校验"这一页真的换人了"**；如果翻页后一个人都不新 → **判定翻页失败，停止并报"翻页没翻动"**，**绝不当成"已采完"**（这是最容易骗自己的地方，单独立规矩） | — |

**⚠️ 我还想请老板批一个小实验（不是必须）**：正式采集**第一次只翻 1 页**时，顺手用桥现成的
`screenshot`/`som_shot` 拍一张结果页截图（**不花 token，只花 1 次页面动作**），**直接看到底有没有「下一页」按钮、长什么样**——
比我在代码里猜快得多。要不要做，老板说。

## 4. 本地粗筛按什么规则打分（0 token，可解释）

### 4.1 三段式

```
第一段：硬条件（本地只做"能不能核对"的部分 → 不满足 = 不收集）
第二段：打分（0~100 + 逐条命中理由）
第三段：兜底（过线的人太少时 → 自动降线，避免把池子筛空）
```

### 4.2 第一段：硬条件（本地怎么处理）

| 来源 | 谁在筛 | 本地还做什么 |
|---|---|---|
| `city_current=南京` | 猎聘搜索条件（服务端筛） | 本地**核对卡片城市字段**：出现明确的外地城市 → 标记 `city_mismatch`，**只记不删**（如实留痕，§报告口径：不拿本地规则偷偷改搜索结果） |
| `education=本科` | 猎聘搜索条件 | 本地核对卡片学历：出现"大专/中专/高中"→ **排除**（写 `dropped`，留痕不删行） |
| 年限 / 统招 / 薪资 / 性别 / 年龄 | **一律不做硬条件**（JD 没写死的、或写死的但口径有矛盾） | 全放进第二段当加减分 |

> 出处依据：①分析报告已经点明"教育经历若为精确匹配会漏硕/博"、年限口径 JD 与 PM 冲突未定
> （`reports/collect_plan_20260915-163727.json` 的 note）→ **凡是口径没定死的一律不用来砍人**，
> 宁可让它进库、交给③逐人判断（误杀比漏收贵得多：漏收的人根本不会出现在老板眼前）。

### 4.3 第二段：打分规则（建议值，老板可整表改）

> **基调分 50**（中间值），然后加减。满分 100，最低 0。**每一分都必须能指到卡片上的原文**（`local_hits` 记命中了哪几个词）。

| 项 | 加分 | 扣分 | 依据 |
|---|---|---|---|
| **关键词命中**（本岗词表，见下） | 行业词或竞品公司名每个 **+8**；技能词每个 **+4**；上限 **+25** | — | PM 原话"主要是**行业需要对口**一些——输送线方向"，行业是这岗真门槛 |
| **活跃度徽章**（卡片顶部） | 今天活跃/在线 **+15**；3天内 **+10**；7天内 **+5**；30天内 **+2**；"隐藏/活跃状态" **0** | — | 越活跃越值得先打招呼（体检实测：加"今天活跃"能砍掉 51%） |
| **学历** | 硕士/博士 **+8**（本科及以上）；本科 **+5** | 大专及以下 **−20**（口径是本科及以上） | JD 明写"本科及以上" |
| **年限** | 3 年及以上 **+5** | 少于 2 年 **−20**；2~3 年 **−10** | JD 写"3年及以上"，但 PM 写"经验不限"→ **只减分不砍人**（口径冲突未定，不误杀） |
| **统招** | 卡片有"统招" **+3** | — | 弱信号，略加分不加锁 |
| **行业反向信号** | — | 现职/经历全是"纯软件 / 非标电气 / 通用设备"且**一个行业词都没命中** **−10** | 防"只看 EPLAN 熟练度"的误伤（PM 明说"画图不重要，重点是行业对口的方案设计"） |

**本岗关键词表（建议：**从①分析报告 `search_keywords` 自动抽词 + 手工补 3 个行业核心词**）**：

- 行业核心词（权重最高，手工补、老板可改）：`输送线`、`提升设备`、`物流机器人`、`托盘输送`、`物流装备`
- 分析报告里的公司词（`search_keywords.竞品对标`）：`德马科技`、`兰剑智能`、`今天国际`、`音飞储存`、`新松`
- 技能词（`search_keywords.技能导向` 拆开）：`EPLAN`、`电控柜`、`电气元件选型`、`BOM`、`变频`、`伺服`
- 职能叫法（`search_keywords.职能相近` 拆开）：`电气设计`、`电控设计`、`电气工程师`

**为什么词表以"①分析报告"为唯一来源**：报告给的是一整串长句（`"电气设计工程师 EPLAN 输送线 南京"`），
**直接拿去搜必然 0 命中**（§报告 §2.1 实测：搜索框是"包含全部关键词"）。所以：**长串 → 拆成可独立命中的词 → 进词表**。
老板若想手写词表，我不做两套来源，会把老板的词覆盖/合并进去。

### 4.4 第三段：兜底（不许把池子筛空）

- **过线阈值建议 60 分**（与③池评的分档线口径一致，§`build_step3_eval_task`：≥80 高 / 60-79 中 / <60 低）。
- **兜底规则**：如果某轮过线人数 < 30 人 → **自动降线到"这一轮分数从高到低第 30 名"的分**（按分取够 30 人），
  并在报告里**用红字写明"这轮触发了兜底降线"**——不许悄悄降线（这是"假成功"最容易藏身的地方）。
- 若这一页**所有人都在 40 分以下** → 不降线，直接判这页是"噪声页"，进停止逻辑（见下）。

### 4.5 落库时每个字段写什么（对应 `schema.sql` 已有列，**不改表**）

| 库列 | 写什么 |
|---|---|
| `source_id` | `fields.res_id_encode`（去重主锚点） |
| `summary_text` | 卡片原文（**不开详情页就有**，§6.2 已实测） |
| `raw_content` | **空**（本轮不采详情页 → 保持空，别拿列表原文冒充全文） |
| `structured` | 从卡片抠出来的字段 JSON（城市/学历/年限/年龄/期望/公司/职位/学校/统招） |
| `local_score` / `local_hits` | 分数 / 命中了哪几个词哪几条规则（**可解释**） |
| `active_badge` | 卡片顶部那行（今天活跃/在线/30天内活跃/隐藏） |
| `round_tag` | `关键字#页码`（如 `电气设计工程师 输送线#p2`） |
| `status` | `new`（过线）/ `dropped`（没过线或学历不符） |

## 5. 什么条件下判定"尾部已飘"就停

> 老板口径（§报告 §7-6）：正常就是**翻页全看完**，池子太大就**加"今日活跃"往下砍**——不是只挑前 20~30 人。

| # | 停止条件（建议值） | 触发后怎么办 |
|---|---|---|
| **1 页数硬顶** | ~~每个关键字最多 5 页~~ → 🔴 **默认不变不再设**（死命令：`--max-pages` 默认 0=不限）；要设限才显式写 N | 停 + 报"到页数硬顶"（只在显式设限时出现） |
| **2 通过率掉线** | **连续 2 页「行业命中=0」**（实现口径，2026-09-16）；外加老板口径的 **连续 10 个人不值得开详情 → 换关键字** | 停 + 报"这词往后没对口的人了"→ **换下一条关键字** |
| **3 翻不动** | 点「下一页」找不到该文本 / 第一行的人没变 | 停 + 报"翻页没翻动"（**≠ 采完**，要老板看） |
| **4 没有新人** | 整页**新增人数 = 0**（全是库里已有的） | 停 + 报"这页没有新人"（也是翻页失败的嫌疑信号） |
| **5 池子只有一页** | 命中总数 ≤ 30 | 翻 1 页就结束（不多余动作） |
| **6 人工刹车** | 老板点「⛔ 停小猎跑腿」 | 立刻收尾、已采的照常落盘（**现成逻辑，直接复用**） |
| **7 配额** | 🔴 **2026-09-16 死命令后此条不再存在**（测试阶段不设人为额度；quota 只记账不拦） | 无动作（真要恢复拦截需在 `quota_config.json` 写 `"enforce": true`；详见《授权矩阵》§3） |

**停下来时，报告必须写清三件事**：停在第几页、**为什么停**、**下一步建议**（"换词 / 加今日活跃 / 去掉学历"/"这词就到头了"）。
这两条留给③当输入，避免下次瞎试。

**我要特别提示的一个"贵的坑"**：第 2 条（连续 2 页通过率 <20%）**会在"排序靠后就是噪声"的池子里提前停下**——
但猎聘的排序未必把最像的人排前面。所以第 2 条**只在"已经翻够 2 页且这词总池子很大（>150 人）"时才允许生效**；
总池子本来就小（本岗实测 121 人 = 5 页）→ **老老实实翻到底**，别用掉线规则省动作。

## 8. 第一次只翻 1 页试点（验收标准）

试点就是**一次正式采集的完整形态，但把页数硬顶设成 1**，跑完当场核对：

| # | 要确认的事 | 怎么确认 |
|---|---|---|
| 1 | 卡片信息**读得全**（转义/换行没吃字） | 抽查 3 条 `summary_text`，人眼比对卡片 |
| 2 | 分数**算得对** | 抽 3 个人**手工按 §4.3 表算一遍**对分 |
| 3 | 「共N位人选」读得到 | 与体检测到的 121 对比（应一致；不一致要查为什么） |
| 4 | 本岗库建出来了 | `job.db` 存在；`candidates` 行数 = 过线人数；`local_hits` 有词；**没有一个人带了详情全文** |
| 5 | **不看简历、不点人** | 桥的额度账本：`extract` 计数跟着页数走，**详情类动作 = 0** |
| 6 | 「下一页」到底能不能点 | 试点**顺手点一次下一页**（就是多 1 页 = 全免费），确认翻页与"翻不动判定"都对 |

试点里发现参数不合适 → **改参数，不改代码**（参数都在一个 JSON 里）；形态本身要改 → 回来重新出计划。

## 10. 顺带要拍的另一件事：逐人匹配由谁执行（报告 §2.5）

这是③的形态，**本轮只拍板、不动手**。

| | 走小猎（现有唯一通道） | **直连 LLM 调用（我的倾向）** |
|---|---|---|
| 花钱 | 每次调用带**全部工具定义 + 人设 + 上下文**（我们量过：工具面租金 ~6,481 token/轮） | 一个固定 prompt + 一个人一个人的输入，**没有工具定义、没有人设** |
| 稳定性 | 它会"发挥"（实测：结论里编过没数据支撑的话、说"已记决策"而系统没记） | **固定 prompt + 固定 JSON 契约**，同一份输入每次都一样 |
| 可缓存/断点 | 不好缓存（会话态） | 天然可缓存：库里 `raw_hash` 输入指纹命中就**不重复付费**；断点续跑 |
| 纪律冲突 | 无（"判断都走小猎"） | **要新开一条"非小猎"的通道** ← 需要老板点头 |
| 可解释 | 判断理由在对话里 | 要**我们**在 prompt 里把"必须引原文/给证据"写死（参考项目 wails 版就没写死 → 它给的分数无凭据） |

**我的建议**：**直连**。理由三条：①这是**机械评分**（照手册打 0-100 + 推荐/待定/不推荐），不是开放判断，
不需要它的"发挥"；②**要能缓存、能断点**——一岗 150 人，跑一半崩了不能从头再烧一遍；③**可复现**：
同一份输入必须给同一个分，否则老板没法复核。
纪律上加一条边界就够：**"开放判断走小猎（要不要接单 / 池子好不好 / 怎么搜）；照表打分走直连（逐人 0-100）"**。
参考项目 wails 版正是这么分工的（**池评**喂 50 条样本走一次，**逐人评分**一人一次），它的输入指纹缓存也是这么做的。
