# 对话交接规范（老对话 → 新对话）

> 版本：v1.1 ｜ 日期：2026-09-16（v1.0：2026-08-31）
> 目的：**解决"一个对话上下文太长 → 效率下降 + 浪费 token"**。核心是：对话是易逝的，**文档是唯一跨对话记忆**。
> v1.1 新增 **§11 ★速查卡约定**：治"新对话光读文档就吃掉 10% 上下文"的**文档黑箱**（必读与叙事分开）。
> 适用范围：任何工作区、任何规模的项目（单人长期项目 / 多人协作项目通用）。
> 来源：提炼自 recruitment-wails 项目《多对话协作工作流》与各阶段完工报告、lietou-agent 交接包（HANDOFF.md）的实际验证经验。

---

## 0. 一条铁律

> **关掉一个对话之前，必须留下文档；打开一个新对话之前，必须先读文档。**
> 新对话**永远不靠"继承老对话的记忆"起步**，只靠交接产物。老对话的上下文用完即弃，token 花在干活上，不花在"回忆"上。

---

## 1. 什么时候开新对话（上下文水位线）

出现以下任一情况，就该**收尾 → 交接 → 开新对话**：

| 触发条件 | 说明 |
|---|---|
| ① 完成一个阶段/里程碑（Phase/M 里程碑） | 天然断点：收尾成本最低 |
| ② 对话明显变"钝" | 回看早期内容要翻很久、AI 开始重复问已答过的问题、答非所问 |
| ③ 上下文将满 | 预估接下来还要干很多活，而当前对话已消耗大半 |
| ④ 换工作区 / 换项目 / 换主题 | 即使对话不长，也按新项目交接（各工作区自持文档） |
| ⑤ 即将进入不同角色阶段 | 设计 → 架构 → 实施，各角色用独立对话，**每层只做一件事** |

**纪律**：一个对话只做一个阶段。做完就停、就交接，不恋战。

---

## 2. 老对话的收尾动作（关对话前 30 分钟内做完）

按顺序执行，全部完成后才允许结束对话：

1. **更新进度文档**（`PROGRESS.md` 或清单的 ★进度状态表）：里程碑状态 / 已完成项 / 验证结果 / 下一步。
2. **写交接包**（`HANDOFF.md`，模板见 §3）：这是新对话的第一份读物。
3. **提交 git**：`git add -A && git commit`，打 tag / 建分支（如 `baseline-v0.4-before`），保证有回滚点。
4. **明确开场顺序**：在交接包里写死"新对话先读哪几个文件、再问什么"。
5. **（可选）归档产物**：完工报告/报告类文档按项目文档目录归档。

---

## 3. 交接包模板（HANDOFF.md · 固定格式）

新对话**第一个**打开的文件。字段全部必填，宁可短不可缺：

```markdown
# 交接包：<项目名>（<阶段/版本>状态）

> 生成时间：<日期> ｜ 交接方式：<本对话 → 新对话>
> 新对话开场顺序：本文件 → <设计方案> → <进度文档> → 再问环境

## 0. 一句话状态
<三行内说清：做到哪了、验证过什么、边界在哪>

## 1. 代码成果
- 交付物总览（产物 | 位置 | 说明）——表格
- 核心模块（模块 | 职责）——表格
- 关键实测结果（✅ 真实值，如"真实闭环 17 候选人"）

## 2. 环境备忘 ⚠️ 新对话开局现查，勿信本快照
<只写"怎么查"，不写"是什么"：如 "python multi-agent/launcher.py status 现查中心库"、
 "conda env lzstudy / PySide6 6.10 已装"、端口、数据库路径、key 位置>

## 3. 运行方式
<常用命令，复制即用>

## 4. 下一阶段方向
<按优先级列出，含"用户测试后反馈"这类北极星>

## 5. 关键教训（新对话别重踩）
<每条一行：现象 + 正确做法。踩过的坑直接写，别让新对话再交学费>

## 6. 交接说明
<工作区结构、活体位置、哪些目录是参考/只读>
```

---

## 4. 新对话的开场动作（收到交接包后 15 分钟内）

1. **按交接包 §开场顺序读文档**：交接包 → 设计方案 → 进度 → 代码结构（**不读老对话**，文档已够）。
2. **现查环境**：交接包的环境备忘只给"查询方法"，用命令核实（tab_id、端口、数据库状态都会变）。
3. **只问 3 个问题**：①当前目标是什么 ②卡在哪 ③下一步做什么。**不追问历史细节**，历史在文档里。
4. **确认理解后立即开工**：先汇报"我对当前状态的理解 + 计划"，确认后再动手，避免方向跑偏。

---

## 5. 文档纪律（防意图衰减）

| 规则 | 做法 |
|---|---|
| 文档是唯一跨对话记忆 | 每个阶段结束必须更新，否则下一个对话失去状态 |
| **决策记录表** | 每条决策必须记录：`\| # \| 决策 \| 结论 \| 理由 \|`——理由写清"当时为什么这么定"，防新对话误读意图 |
| 验收标准前置 | 每个任务包/Phase 在分配时写清验收标准（能编译/能跑通/接口契约），验收对照标准逐条查，不凭感觉 |
| 命名约定 | 项目文档统一放 `<工作区>\工作文档\`；交接包固定名 `HANDOFF.md`、进度固定名 `PROGRESS.md`、设计方案 `<项目名>设计方案.md` |
| 完工报告 | 每个任务包完成写一份 `<任务包>·完工报告.md`：改动清单 / 测试结果表 / 与任务偏差 / 遗留与真机验证步骤 |

---

## 6. 汇报协议（省 token 的关键）

向"决策者"（经理/自己回顾）汇报**只报摘要，固定格式，不报代码细节**：

```
<阶段/任务包>完成情况：
1. 完成度：（全部 / 部分 / 阻塞）
2. 质量结论：（能编译 / 能跑通 / 有测试？对照验收标准逐条）
3. 与设计的偏差：（如有，说明原因；无则写"无"）
4. 下一步建议：（继续下一阶段 / 需决策某点 / 需返工）
```

- 决策者说"继续" → 派发下一步；说"要改" → 转成修改任务。
- 决策者**不读实施代码**，只在业务取舍、设计偏差、阻塞三件事上介入。

---

## 7. 上下文管理规则（防 token 浪费）

1. **一个对话只做一个阶段**：设计对话不读实施代码（上下文留给业务决策）；实施对话不重读设计长文（只读任务包）；架构对话负责"替决策者读代码判质量"。
2. **上下文长了 → 开新对话，不硬撑**：设计对话长了开架构对话；架构对话长了开实施对话；实施做完一个 Phase 就停。
3. **实施对话做完一个任务包就交接**：回报 → 视情况续用或新开（默认新开，成本最低）。
4. **不要**让一个对话从头到尾干完大项目——上下文爆炸必然导致质量下降 + token 浪费。

---

## 8. 角色分工（多人协作时启用；单人项目可合并）

| 角色 | 对话 | 职责 | 边界 |
|---|---|---|---|
| 部门经理（决策者） | 设计对话 | 讨论意图、确认设计、最终拍板 | 不读实施代码；只收摘要汇报 |
| 小组长（架构） | 架构对话 | **读实施成果判质量** → 拆任务 → 派发 → 验收 → 报摘要 → 更新进度表 | 不写实施代码；业务取舍回报经理 |
| 小组成员（实施） | 实施对话 | 读任务 → 编码 → 验证 → 提交 → 回报 | 只做分配任务，不擅自扩大范围 |

> 单人长期项目：自己同时扮演三角色，但**角色动作不能省**——尤其"收尾写交接包"和"新对话先读文档"。

---

## 9. 开场白模板（新对话第一段，复制即用）

```
你是本项目的<角色>（小组长/小组成员/实施工程师）。
先读交接包：《HANDOFF.md》（<工作区路径>），按其中"开场顺序"读完相关文档。
读完后，用 3 句话向我确认：①项目当前状态 ②本次要完成的目标 ③你的执行计划。
确认后再动手。边界：<按角色填>。
```

## 11. ★速查卡约定（v1.1 · 2026-09-16 新增）——治"文档黑箱"

> **症状**（老板 2026-09-16 原话）：「新对话啥也不干，光读交接文档就用了 10%，感觉进入了文档黑箱」。
> **病因不是"报告该存在"，而是"必读部分与叙事部分没分开"**：新对话被迫从头读到尾，才敢动手。
> **治法**：只做最轻的两件——**速查卡 + 分节寻址**。⚠️ 这**不是**"工作文档分层"（那只目录体系/多文件拆分仍在"不做"清单里）。

### 11.1 实测（2026-09-16，只量字节不读内容；中文 markdown ≈ 2.5 字节/词元，**是数量级估算**）

| 量 | 字节 | ≈词元 |
|---|---|---|
| `工作文档\` 全部 27 份 | 592,032 | ~237,000 |
| 其中 `PROGRESS.md` 单份 | 122,995 | ~49,000 |
| 《②正式采集…衔接报告》**全文** | 37,724 | ~15,090 |
| 该报告开头的 **★速查卡**（14 行） | 2,178 | ~871 |
| **最小读集** = 速查卡 + 本场开工那一节（§4.1） | 3,742 | ~1,497（= 全文的 **9.9%**） |

→ 结论：**速查卡这一页就够开工**；读全文比读最小集贵 **10 倍**，而多读的部分大多是叙事（复盘/事故/我判断错了什么），**开工前不需要**。

### 11.2 约定（**从下一份报告开始**；老文档**不返工**）

1. **每份衔接报告/完工报告的第一屏必须是 `## ★ 速查卡`**，**≤1.5KB 字节**（≈600 词元，写完量一下）。
2. 速查卡**只放"新对话开工必需的六件"**，顺序固定：
   ① 环境（python/面板/桥/扩展 + **用前现查**的那几条）② 本场结论**一句话**
   ③ **本场开工第一件事**（点哪一节）④ 硬纪律 ⑤ **最容易踩的坑**（≤3 条）
   ⑥ **要读细节时点这些节**（分节寻址）。
3. **不写"为什么"**：复盘、事故、"我判断错了什么"、讨论过程**一律留在叙事区**（§2/§7 之类）。
   速查卡是**事实与地址**，不是文章。
4. **分节寻址**：速查卡最后一行必须是 `§x.y（干什么）｜§x.y（干什么）` 这种指针列表；
   **禁止**写"详见全文""见上文"。（一节一个主题，标题里带**确定度**：`【已定】/【已实测】/【已查证】/【未验】/【待拍板】`。）
5. **老文档不动**：旧报告的标题/结构不改（引用它的地方太多；返工成本 > 收益）。
   本约定**只约束新写的报告**。
6. **新对话的开场白里写死最小读集**：`先只读 ★速查卡那一页；不足用时再点名读 <哪几节>`，
   并明确"**别一上来通读全文**"。
7. **上限是真的上限**：速查卡超过 1.5KB 时，砍的是**叙事**（往下搬），不是"把速查卡写紧凑"。
