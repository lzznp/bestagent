# 协作工作流草案（5 步循环 · 实验性）

> 版本：v0.1 草案 ｜ 日期：2026-09-01
> 定位：**可选的工作方式提议，不是纪律**。记录"怎么用 DSH 强工具干活"的一个想法——刚考虑、不成熟，以后对话知道有这个想法即可，按需取用，不必严格遵守。
> 关联：`《对话交接规范.md》`（纪律，必守）｜ `《HANDOFF.md》`（交接包）｜ `《PROGRESS.md》`（进度档案）

## 1. 为什么会有这个想法

- **旧工作方式（复制粘贴循环）**：PyCharm + 网页版讨论 + codewhale 侦察出 md 报告 + 手动搬运代码/报错。
  - 好处：深度参与、知道每个文件的作用
  - 痛点：慢、累——一个人同时干四个角色的活（经理/架构/实施/测试）；讨论无锚点，方向容易带偏
- **DSH 强工具出现后**：agent 能自己读文件/写文件/跑命令/自己改/自己测/自己汇报（M1.1 岗前分析、M2a 池子评估已验证）。
- **想法**：把"实施+测试"交给 agent，人只做"定目标 / 派活 / 验收 / 纠错"——你从搬运工变验收官，数字合伙人的雏形。

## 2. 5 步循环（核心想法）

```
① 人（Web 对话）：定目的声明 + 验收标准
② 人：派活（任务包，写清楚干什么/验收什么）
③ agent：本地干活（读代码 → 写代码 → 自己跑 → 报错自己修 → 自己测）
④ agent：交完工报告（改动清单 / 每个文件干什么用 / 测试结果 / 与设计偏差）
⑤ 人：PyCharm 抽查 + 跑一遍 → 验收/纠错 → 更新 PROGRESS.md → 回 ②（不满意打回）
```

- 人的参与点：**定目标、派活、验收、纠错**（每轮动手约 1 次）
- agent 的参与点：**侦察、实施、测试、汇报**（每轮动手 3-4 次）
- 对比旧流程：人每轮动手 4-5 次 → 1 次；且每轮有完工报告做锚点，方向不易漂

## 3. 深度参与怎么保底（想用深度参与时的机制）

1. **完工报告必读**：改动清单+文件用途+测试结果，读报告即知全貌
2. **PyCharm 代码抽查**：看不懂就问 agent"这段为什么这么写"
3. **决策记录表**：关键决策落文档写清理由（防带偏的锚）

## 4. 使用方式（重要）

- **可选、非强制**：不设验收门槛，不违背时也不必解释。觉得合适就用，不合适就回老办法。
- 与纪律的关系：《对话交接规范》的"目的声明对齐 + 小步验证 + 文档更新"是**纪律**（照旧必守）；本草案只是"活具体怎么干"的提议。
- 试点建议：下次任务（如 M2 采集模块）按此循环跑一次，跑完对比感受，再决定推广/调整。
