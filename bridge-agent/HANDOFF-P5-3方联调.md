## 1. 底座定位（多轮讨论定稿，勿再动摇）

- **底座 = 通用执行器（工具），不是助手**。操作自主、业务纯执行（DESIGN-BASE D3）。
- **业务判断一律在底座外**：JD 理解/搜索条件/相关性/是否采集 → 上层（用户 + 匹配/调度 agent）。底座通过任务描述接收条件，不持有业务上下文。
- **判据**：一个知识/规则"需要懂业务才能写"吗？需要→上层；不需要→底座手册。
- **手册 = 纯站点操作知识**（怎么点/什么行为/什么坑），不含业务决策（如"结果不相关就停"是上层的事）。

## 5. 3方联调方法论（新对话的主线工作流）

**3方 = 用户（提供 JD + 真值判定）+ 讨论层（分析页面/生成条件/验收标准）+ agent（执行）。**

每个页面按这个循环测：

```
① 页面分析（讨论）    这个页面是干什么的？我们以后想在这里实现什么功能？
                       agent 要做到什么程度算"能做到"？（验收标准）
② 条件生成（讨论）    拿一份真实 JD → 讨论出搜索条件（城市/年限/学历/关键词...）
                       → 写成任务描述（业务判断在此完成，不进手册）
③ agent 执行          底座按任务描述 + 站点手册执行（可先 --dry-run 看决策再正式跑）
④ 人工判定（用户）    结果对不对？动作点没点对？内容抓没抓对？
                       → 通过：必要时把"更好的操作方法"更新进手册
                       → 失败：归因——手册问题？任务描述问题？站点改版？代码 bug？
```

**验收归因四象限**（DESIGN-BASE D10，新对话沿用）：
- 决策错 → 改任务描述/讨论条件（不改代码）
- 站点操作方法错 → 改手册文字（人工实测后更新）
- 站点改版 → verify 检测 + 更新手册
- 代码 bug → 才改代码

**每页验收产出**：页面作用说明 + 验收标准 + 试跑记录（事件流）+ 用户判定 + （必要时的）手册更新。建议记入 `logs/page_tests.jsonl` 或对话内表格。
