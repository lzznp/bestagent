### 1.1 配方表 schema1 → schema2（多页面配方库）

**问题**：原 `page_recipes.json` 只挂一个页面（硬编码），`load_recipes()` 无 URL 概念 → 无法让"多个数字员工副本 / 多个页面"共享配方。

**改动**：
| 文件 | 改动 |
|---|---|
| `agent/page_recipes.json` | schema1 单页 → **schema2**：`pages` 按 URL 键组织 + `default_page`。原 29 组配方（24 confirmed / 5 pending）+ 7 behaviors + 5 pending_items 完整保留，包进 `pages["h.liepin.com/search/getConditionItem"]` |
| `agent/recipe_exec.py` | ① `load_recipes(path, url=None)`：无 url 返回默认页；有 url 按"URL 路径子串优先→域名兜底"匹配（复用 `knowledge_config.json` 的 `match_knowledge` 模式），命中返回对应页面 dict（含 `_page_key`/`_recipes` 标注）② `execute_spec(..., url=None)` 支持按 URL 取配方 ③ 搜索按钮文本从配方 search 组读取（不再硬编码"搜 索"） |
| `agent/jd_to_spec.py` | `jd_to_spec(..., url=None)` 支持按目标页面取配方 options |
| `agent/migrate_recipes_schema2.py` | 一次性迁移脚本（schema1→schema2，已执行，29 组完整保留） |

## 2. 多 Agent 架构讨论（战略定稿）

> 新对话若继续多 Agent 架构，以此为共识，勿再动摇。

### 2.1 核心决策（8 条，全部用户确认方向）

| # | 决策 | 结论 |
|---|---|---|
| 1 | **不做"集中攻坚"** | 猎头非"努力必有产出"，不值得为"10 员工做一岗"设计专门机制 |
| 2 | **员工 = 无状态通用劳动力** | 接子任务→干活→上报结果，员工互不通信 |
| 3 | **不需要"协同协议"** | 多员工协作的本质是"调度器管账号×岗位×候选人分配"，不是员工间通信 |
| 4 | **存储双轨** | 本地 SQLite（工作日志/草稿）+ 服务器 PostgreSQL（唯一共享中心库，上报目标） |
| 5 | **避重复靠中心库"岗位进度表"** | 开工前查"岗位X是否有人负责" |
| 6 | **配方表 = 共享资产** | 10 员工读同一份，按 URL 挂载（本轮已实现地基） |
| 7 | **Ollama = 决策推理** | JD→spec 等，接在员工决策层（本地模型） |
| 8 | **两个独立系统** | 总控（调度/看状态）+ 配方表生成维护（预测试→产出 JSON） |

### 2.2 关键洞察（用户自己点破，很珍贵）
- **"集中攻坚"是伪命题**：真问题是"账号有查看量风控 + 打招呼 50 次/天限制"。多账号 ≠ 多员工/多电脑——账号池（一员工切多账号）比多员工协同轻量得多。
- **避重复 = 共享一张"岗位进度表"**，不需要通信协议。
- **资源-岗位配比公式**：目标月成交量 × (1÷成交率) = 需处理岗位数/月；岗位数 ÷ 单账号月可安全处理数 = 需账号数。**这是运营参数，上线后用真实数据调，不是架构要写死的。**

## 6. 关键教训（新对话别重踩）

1. **业务层过滤 vs 执行器**：JD→spec 时，company/精确职位名会让结果 0——这类"该选什么条件"是业务判断，应留在上层，不进执行器。执行器只负责"怎么点"。
2. **扩展注入会"拾取但不回报"**：任务状态停在 `executing`（picked 有值、finished 为 null）且 list_tabs 正常 = 扩展注入页面失败 → 让用户刷新标签/重载扩展，不是代码 bug。
3. **不要按固定编号操作**：页面元素数波动，一律文本定位（click_by_text）。
4. **配方表是纯数据 + 按 URL 挂载**：这是"10 员工共享知识"的地基，改配方一处全生效，不要退回"每副本各一份"。
